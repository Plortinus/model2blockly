\chapter{Ejemplo conductor y evaluación}
\label{chap:casos-evaluacion}

La evaluación de Model2Blockly busca comprobar si el enfoque es viable. En concreto,
se analiza si es posible generar editores Blockly reutilizables a partir de
descripciones de dominio, sin programar cada editor desde cero. Para ello se usa
un ejemplo conductor, verificaciones técnicas y pruebas automáticas.

No se evalúan aprendizaje ni usabilidad con usuarios finales. Ese tipo de estudio
necesitaría participantes, tareas y métricas de interacción. Aquí la evaluación
se centra en la ingeniería de la solución: rutas Ecore y \texttt{.m2b},
artefactos generados, validaciones, modelo intermedio y pruebas automáticas.

El capítulo comienza con la estrategia de evaluación y la presentación del
ejemplo conductor. A continuación, se describe AppMaker mediante las dos rutas
de entrada y se analiza la cobertura funcional alcanzada. Después se presentan
las verificaciones técnicas, los resultados frente a los objetivos y la
correspondencia entre el metamodelo y el editor Blockly generado. Finalmente,
se discuten las limitaciones del estudio y se sintetizan sus conclusiones.

\section{Estrategia de evaluación}
\label{sec:estrategia-evaluacion}

La estrategia de evaluación combina cuatro tipos de evidencia:

\begin{enumerate}
  \item un ejemplo conductor, AppMaker, definido como metamodelo Ecore anotado
  y como fichero textual \texttt{.m2b};
  \item inspección y verificación sintáctica de los artefactos generados;
  \item pruebas automáticas sobre modelo intermedio, adaptadores y generadores;
  \item artefactos de entrega reproducibles, incluyendo update site p2, demos
  desplegadas e informes de generación.
\end{enumerate}

La Figura \ref{fig:flujo-evaluacion} muestra cómo se relacionan estas fuentes
de evidencia. El dominio se expresa como \texttt{app\_maker.ecore} y como
\texttt{app\_maker.m2b}. Ambas entradas convergen en la cadena
\texttt{EditorSpec}--HTML/JavaScript y después se contrastan mediante informes,
comprobaciones sintácticas y pruebas automáticas.

Estas fuentes responden a cuatro preguntas. Primero, si la ruta Ecore puede
generar un editor Blockly funcional desde un metamodelo anotado. Segundo, si la
ruta textual \texttt{.m2b} puede describir el mismo lenguaje de bloques y
normalizarse hacia el mismo modelo intermedio. Tercero, si los artefactos
generados son técnicamente coherentes y pueden verificarse de forma repetible.
Cuarto, si el resultado puede entregarse como herramienta instalable y como demo
web revisable.

La primera fuente analiza la reutilización de la cadena generativa. Un generador
de editores de bloques no resulta convincente si la salida es un HTML preparado
manualmente o si cada entrada exige un generador distinto. Por ello, AppMaker se
describe por las dos rutas: como metamodelo Ecore con anotaciones y como fichero
textual \texttt{.m2b}. Ambas formas se transforman a \texttt{EditorSpec}; la
ruta Ecore y la ruta textual cuentan con salidas generadas en el repositorio y
con demos desplegadas públicamente para la revisión externa del editor final.

La segunda fuente comprueba que la generación produce ficheros revisables y
sintácticamente válidos. En particular, los ficheros JavaScript generados para
las salidas incluidas se han comprobado con \texttt{node --check}, lo que permite
detectar errores de sintaxis sin ejecutar el editor completo en el navegador.
Esta comprobación no sustituye a una prueba funcional interactiva, pero sí
reduce el riesgo de que el generador emita código JavaScript mal formado.

La tercera fuente son las pruebas JUnit del proyecto. Estas pruebas no dependen
de la interacción manual con el navegador y permiten comprobar comportamientos
internos: mapeos desde Ecore, normalización desde la ruta textual \texttt{.m2b},
comportamiento del modelo intermedio y generación HTML/JavaScript.

\section{AppMaker por las dos rutas de entrada}
\label{subsec:appmaker}

AppMaker representa una aplicación visual con páginas, componentes, acciones,
navegación y fuentes de datos. El resultado generado es un editor de modelado:
el usuario no recibe una aplicación final cerrada, sino un entorno visual para
construir modelos de aplicaciones. El dominio incluye referencias cruzadas
representativas: un \texttt{ListView} referencia una fuente de datos, y una
acción \texttt{Navigate} referencia una página destino. También se usan
plantillas de código para generar una representación textual de la aplicación.

La ruta Ecore parte de \texttt{model/app\_maker.ecore}. La estructura del dominio
se expresa como metamodelo EMF y la información específica de Blockly se añade
mediante anotaciones. Las anotaciones con fuente \texttt{blockly} controlan
aspectos de sintaxis visual, las anotaciones \texttt{ui} describen metadatos de
interfaz, las anotaciones \texttt{code} definen plantillas de generación y las
anotaciones \texttt{runtime} seleccionan opciones de ejecución.

La ruta textual parte de \texttt{examples/app\_maker.m2b}. En este fichero se
declaran categorías, clases, atributos, contenciones, referencias, entradas de
valor, validaciones y opciones de presentación con una sintaxis más compacta que
el XML/XMI de Ecore. El fichero \texttt{.m2b} no representa una instancia de una
aplicación AppMaker, sino la definición del lenguaje de bloques AppMaker que se
transforma a \texttt{EditorSpec}.

Para que el caso de estudio sea revisable, la memoria no se limita a describir
AppMaker de forma narrativa. El caso se documenta con fragmentos de código de
entrada, fragmentos de modelos generados y capturas de pantalla de los editores.
Los Listados \ref{lst:appmaker-dsl} y \ref{lst:appmaker-ecore} muestran partes
representativas del DSL textual \texttt{.m2b} y de la especificación Ecore
evaluada. El Listado
\ref{lst:appmaker-xmi} muestra el modelo intermedio obtenido y el Listado
\ref{lst:appmaker-generated-code} muestra un fragmento del generador JavaScript
emitido para uno de los bloques del dominio. Las Figuras
\ref{fig:appmaker-ecore-editor}, \ref{fig:appmaker-dsl-editor},
\ref{fig:appmaker-ecore-generation-report} y
\ref{fig:appmaker-validation-workspace} complementan esos fragmentos con
evidencia visual de las salidas generadas.

Las dos rutas producen una instancia del modelo intermedio
\texttt{EditorSpec}. Esta instancia se serializa como XMI dentro de la carpeta
\texttt{intermediate/} de la salida generada. A partir de ese modelo se generan
los artefactos HTML/JavaScript, las validaciones, las páginas de edición, el
informe de generación, el modelo de ejemplo y la vista Blockly de reglas de
validación.
Además, el editor generado permite exportar el modelo creado por el usuario como
JSON y como XMI de instancia del dominio. Por lo tanto, en la evaluación se
distinguen dos niveles: el XMI intermedio \texttt{EditorSpec}, usado por la
cadena de generación, y el XMI de instancia, producido por el editor generado.

El Listado \ref{lst:appmaker-xmi} muestra un fragmento del XMI generado por la
ruta Ecore. Este artefacto permite inspeccionar el resultado de la transformación
antes de generar JavaScript: las clases y relaciones del dominio ya aparecen como
categorías, tipos de bloque, campos y entradas tipadas.

\begin{lstlisting}[caption={Fragmento del modelo intermedio XMI generado para AppMaker}, label={lst:appmaker-xmi}]
<blocklyspec:EditorSpec domainName="AppMaker"
    nsURI="http://www.example.org/appmaker"
    codeLanguage="javascript" codeFileExtension="js">
  <categories name="Pages" label="Pages" colour="260"/>
  <categories name="Components" label="Components" colour="160"/>
  <categories name="Data" label="Data" colour="210"/>
  <blockTypes typeName="App" label="App" colour="260"
      categoryName="Pages" connectionType="NONE">
    <fields name="name" defaultValue="Task Tracker" required="true"/>
    <statementInputs name="dataSources" checkType="DataSource"
        lowerBound="1" upperBound="20"/>
    <statementInputs name="pages" checkType="Page"
        lowerBound="1" upperBound="20"/>
  </blockTypes>
</blocklyspec:EditorSpec>
\end{lstlisting}

El Listado \ref{lst:appmaker-generated-code} muestra un fragmento representativo
del código JavaScript producido por el generador para AppMaker. Este código
ilustra que la salida no se limita a pintar bloques: también se emiten funciones
que recorren el workspace, leen campos y referencias, y serializan el modelo
visual en una representación textual exportable.

\begin{lstlisting}[caption={Fragmento legible del generador JavaScript emitido para \texttt{ListView}}, label={lst:appmaker-generated-code}]
javascript.javascriptGenerator.forBlock['ListView'] = function(block) {
  var emptyText = block.getFieldValue('emptyText');
  var source = block.getFieldValue('source');
  var itemTitle =
    javascript.javascriptGenerator.valueToCode(block, 'itemTitle', 0) || 'null';

  return '{' +
    '"_type": "ListView", ' +
    '"_blockId": ' + JSON.stringify(block.id) + ', ' +
    '"emptyText": ' + JSON.stringify(emptyText) + ', ' +
    '"source": ' + JSON.stringify(source) + ', ' +
    '"itemTitle": ' + itemTitle +
  ' },\n';
};
\end{lstlisting}

\section{Verificaciones técnicas}
\label{sec:verificaciones-tecnicas}

Además del ejemplo conductor, se han realizado verificaciones técnicas sobre los
artefactos generados y sobre el código del proyecto. La primera verificación
consiste en comprobar que los ficheros JavaScript generados no contienen errores
de sintaxis. Para ello se ha usado una comprobación sintáctica de Node.js sobre
la salida generada. No se detectaron errores de sintaxis en los ficheros
revisados, lo que aporta una comprobación reproducible sobre la corrección
sintáctica de la salida JavaScript.

La segunda verificación es la existencia de pruebas JUnit por capa. El proyecto
incluye 142 pruebas distribuidas en seis clases. La Tabla
\ref{tab:pruebas-evaluacion} resume su cobertura.

La organización de las pruebas sigue la misma división que la arquitectura. Si
falla una prueba del adaptador Ecore, el problema está en la ruta de entrada. Si
falla una prueba del generador HTML, el problema está en la salida. Si falla una
prueba del modelo intermedio, puede haberse roto el contrato común entre capas.
Esta trazabilidad ayuda a mantener el proyecto.

Además de las pruebas JUnit, el repositorio incluye verificaciones de entrega. El
script \texttt{verify:plugin} comprueba metadatos de bundles, feature, update
site, versión \texttt{1.0.9.qualifier}, entorno \texttt{JavaSE-21} y presencia de
artefactos generados. Los scripts \texttt{verify:docs},
\texttt{verify:domain-xmi} y \texttt{verify:patch} cubren documentación, carga
EMF del XMI de instancia exportado y el flujo de edición/aplicación de reglas de
validación.
También existe un \emph{smoke test} de navegador para cargar los editores
generados, tratado como verificación complementaria porque depende de disponer de
Playwright en el entorno local.

\section{Correspondencia entre metamodelo y editor Blockly}
\label{sec:correspondencia-expresividad}

La evaluación no asume que un metamodelo Ecore y un editor Blockly tengan la
misma expresividad. La relación entre ambos es una correspondencia práctica
definida por el generador. Algunos elementos de Ecore se trasladan de forma
directa: clases concretas a tipos de bloque, atributos a campos, contenciones a
entradas de sentencias, referencias no contenidas a desplegables dinámicos y
cardinalidades a reglas de validación. Otros elementos requieren decisiones de
sintaxis concreta, como colores, etiquetas, categorías, widgets, disposición en
línea o campos usados para mostrar referencias.

También existen elementos de Ecore que no tienen una representación Blockly
equivalente completa en esta versión. Por ejemplo, las restricciones OCL
arbitrarias, algunas relaciones bidireccionales complejas, la importación
genérica de instancias XMI existentes, los tipos de datos personalizados con
semántica rica o reglas globales sobre colecciones no se traducen de forma
general. La herramienta cubre patrones frecuentes y genera advertencias, pero no
convierte el editor Blockly en un editor EMF completo.

En sentido contrario, el editor Blockly contiene información que no pertenece al
metamodelo abstracto: color, toolbox, tooltip, texto visible, orden de campos,
shadow blocks, vista de validaciones, botones de exportación o preview HTML.
Esa información describe una sintaxis concreta y una experiencia de edición, no
la semántica estructural del dominio. Por ello se almacena como anotaciones o
metadatos y no debe confundirse con el metamodelo de dominio.

La conclusión es que Model2Blockly busca una equivalencia útil para generación,
no una equivalencia semántica total. El editor generado permite crear y exportar
modelos que respetan la estructura principal del metamodelo dentro de las reglas
soportadas, pero hay modelos Ecore válidos que pueden requerir extensiones del
generador para editarse cómodamente en Blockly, y hay decisiones visuales de
Blockly que no modifican la expresividad del metamodelo.

\section{Limitaciones de la evaluación}
\label{sec:limitaciones-evaluacion}

La evaluación realizada tiene límites. En primer lugar, AppMaker ha sido
diseñado por el autor del proyecto. Aunque cubre varias estructuras, no equivale
a una evaluación con usuarios externos ni con modelos industriales de gran
tamaño. En segundo lugar, las comprobaciones generadas se implementan como
advertencias y confirmaciones de exportación, no como un mecanismo formal de
verificación semántica completa. En tercer lugar, la comprobación con
\texttt{node --check} solo verifica sintaxis JavaScript, no interacción visual
en todos los navegadores.

Además, la ruta Ecore se ha evaluado con un metamodelo representativo, pero no
con un conjunto amplio de metamodelos heterogéneos. Funciones como la
sincronización bidireccional completa en todos los runtimes, restricciones OCL
arbitrarias, importación genérica de XMI o generación de código con análisis
semántico avanzado quedan fuera del alcance actual. La edición visual de
validaciones también debe interpretarse de forma acotada: solo se aplican de
vuelta a la fuente las reglas que tienen una traducción directa.

Estas limitaciones no invalidan la evidencia técnica, pero sí acotan su
interpretación. Model2Blockly aporta evidencia de una cadena generativa funcional y
reutilizable en el caso estudiado. Una evaluación futura podría incluir más
metamodelos, medir el esfuerzo frente a una implementación manual en Blockly y
realizar estudios con usuarios finales.

\section{Conclusión de la evaluación}
\label{sec:conclusion-evaluacion}

El ejemplo conductor y las verificaciones técnicas apoyan la idea central del
TFM. Model2Blockly no genera un editor escrito manualmente, sino un editor
derivado de descripciones de dominio. La ruta Ecore permite generar desde
metamodelos. La ruta textual \texttt{.m2b} permite definir lenguajes de bloques
de forma compacta. El modelo intermedio permite mantener el contrato entre
transformación y generación.
La disponibilidad del update site p2, las demos desplegadas y los informes de
generación complementan esa evidencia al mostrar que la propuesta puede
instalarse, ejecutarse y revisarse fuera del entorno de desarrollo del autor.
