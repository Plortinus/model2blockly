\chapter{Implementación de Model2Blockly}
\label{chap:implementacion}

Este capítulo explica la implementación de Model2Blockly siguiendo el recorrido
de una ejecución completa. A diferencia del capítulo anterior, centrado en el
diseño y la arquitectura, aquí se identifican las tecnologías, clases y
operaciones que materializan cada etapa de la cadena generativa.

La exposición comienza con la instalación del complemento en Eclipse y con
\texttt{01\_basic\_structure}, un caso cerrado que muestra qué describe la
entrada, cómo se transforma y qué editor produce. Después se presentan el flujo
interno, la organización del código y otros cinco ejemplos acotados. Los seis
ejemplos con doble representación forman versiones sucesivas de un mismo
dominio de gestión de proyectos:
cada directorio conserva un ejemplo ejecutable completo, pero añade una familia
de capacidades respecto al anterior. Sus nombres base describen la etapa
mostrada, como \texttt{basicStructure.ecore} y
\texttt{basicStructure.m2b}. Fuera de esos seis ejemplos se añade un caso específico para
capacidades exclusivas de Ecore. Este corpus aísla las reglas explicadas en el
resto del capítulo. Sobre esa base se detallan la carga y validación de las
entradas, el contrato \texttt{EditorSpec}, los
adaptadores Java, el generador HTML/JavaScript y el comportamiento en el
navegador. El capítulo termina con la integración y distribución en Eclipse,
las entradas independientes y las pruebas de implementación.

\section{Instalación y uso del complemento}
\label{sec:ejecucion-model2blockly}

Antes de detallar las clases internas, esta sección presenta cómo instalar y
utilizar el complemento.

\subsection{Instalación del complemento}

\begin{samepage}
Model2Blockly requiere una distribución de Eclipse compatible con Java 21 y
ejecutada con un JDK 21. El complemento se instala desde este repositorio p2:

\begin{center}
  \url{https://plortinus.github.io/model2blockly/update-site/}
\end{center}
\end{samepage}

La instalación se realiza con los siguientes pasos:

\begin{enumerate}
  \item abrir \texttt{Help -> Install New Software...} en Eclipse;
  \item pulsar \texttt{Add...}, asignar un nombre como \texttt{Model2Blockly}
  y registrar la URL anterior;
  \item mantener activa la opción \texttt{Contact all update sites} para
  resolver las dependencias, seleccionar la feature de Model2Blockly y
  continuar con el asistente;
  \item aceptar las condiciones de la instalación y reiniciar Eclipse cuando
  se solicite.
\end{enumerate}

La instalación queda disponible cuando el menú contextual de un fichero
\texttt{.ecore}, \texttt{.m2b} o \texttt{.model2blockly} muestra el comando
\texttt{Generate Blockly Editor}.

\subsection{Uso del complemento}

Una vez instalado el complemento, la acción de generación se aplica a un
fichero de entrada situado en el espacio de trabajo. El ejemplo empleado para
la primera ejecución se distribuye en el repositorio público de
Model2Blockly.\footnote{Carpeta del ejemplo en GitHub:
\url{https://github.com/Plortinus/model2blockly/tree/main/examples/feature_pairs/01_basic_structure}.}
Después de descargar o clonar el repositorio, la carpeta \path{examples/}
se importa en Eclipse como el proyecto independiente
\texttt{model2blockly.examples}. El primer ejemplo queda entonces visible en
\path{feature_pairs/01_basic_structure}, sin necesidad de buscarlo dentro de
uno de los bundles del complemento.

Al pulsar con el botón derecho sobre un fichero \texttt{.ecore} o
\texttt{.m2b}, Eclipse muestra la acción \texttt{Generate Blockly Editor} en el
menú contextual. La Figura~\ref{fig:plugin-context-menu} muestra esta opción;
al seleccionarla comienza la generación del editor.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.90\textwidth]{assets/blockly/generate_blockly_editor_context_menu.png}
  \caption{Acción \texttt{Generate Blockly Editor} en el menú contextual de un
  fichero \texttt{.ecore} o \texttt{.m2b}}
  \label{fig:plugin-context-menu}
\end{figure}

Para utilizar la ruta Ecore con este ejemplo se siguen estos pasos:

\begin{enumerate}
  \item importar en Eclipse la carpeta raíz \path{examples/} mediante
  \texttt{File -> Import -> Existing Projects into Workspace}; Eclipse la
  muestra como el proyecto \texttt{model2blockly.examples};
  \item seleccionar el fichero \path{basicStructure.ecore} dentro de ese directorio;
  \item pulsar con el botón derecho sobre el fichero y seleccionar
  \texttt{Generate Blockly Editor};
  \item revisar el informe \path{basicStructure_generated/generation_report.html}
  que Eclipse abre al finalizar la generación;
  \item abrir en un navegador el editor generado mediante
  \path{basicStructure_generated/html/BasicStructure_standalone.html}.
\end{enumerate}

La ruta textual se ejecuta de la misma forma seleccionando
\path{basicStructure.m2b} en
el mismo directorio. En los dos casos, si no se detectan errores, la
herramienta crea junto a la entrada un directorio con el sufijo
\texttt{\_generated}. El directorio contiene el informe de generación, una
serialización XMI de \texttt{EditorSpec}, las definiciones de bloques, la paleta,
los scripts de generación y validación, un modelo de ejemplo y las páginas HTML
del editor.

Conviene distinguir las dos ejecuciones implicadas. La primera se realiza en
Eclipse y transforma la descripción del dominio en artefactos web. La segunda se
realiza en el navegador al abrir la página autónoma
\texttt{*\_standalone.html}; en ella,
el usuario construye modelos del dominio mediante bloques, ejecuta las
validaciones generadas y exporta el resultado como JSON, XMI o código textual.

\subsection{Ejemplo 01: del metamodelo al editor Blockly}

El directorio \path{01_basic_structure} contiene dos representaciones
alternativas del mismo dominio de planificación de proyectos. No son dos
fragmentos que deban leerse juntos: cada fichero constituye por sí solo una
entrada completa para el complemento. \path{basicStructure.ecore} es un fichero
de metamodelo Ecore; \path{basicStructure.m2b} es un modelo textual escrito con
el DSL de Model2Blockly. El objetivo del ejemplo es comprobar que ambas
representaciones llegan al mismo editor.

\subsubsection{El fichero \texttt{basicStructure.ecore}: un metamodelo Ecore}

El \texttt{EPackage} raíz de \path{basicStructure.ecore} se denomina
\texttt{basicStructure}; \texttt{nsURI} identifica de forma estable ese paquete
y \texttt{nsPrefix} proporciona el prefijo usado en su serialización XML.

La Figura \ref{fig:basic-structure-ecore} representa ese contenido mediante una
clase gráfica, más compacta que la serialización XMI del fichero.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.96\textwidth]{../../examples/feature_pairs/01_basic_structure/basicStructure class diagram.jpg}
  \caption{Metamodelo Ecore definido en \texttt{basicStructure.ecore}}
  \label{fig:basic-structure-ecore}
\end{figure}

Los elementos de la figura tienen el significado siguiente:

\begin{itemize}
  \item \texttt{Project} es la clase raíz. Su atributo \texttt{name} es un
  \texttt{EString} y tiene como valor predeterminado
  \texttt{Website redesign}.
  \item \texttt{WorkItem} es una clase abstracta. Define el tipo común de los
  elementos que pueden formar el trabajo de un proyecto, pero no puede
  instanciarse directamente.
  \item \texttt{Task} hereda de \texttt{WorkItem}. Su atributo
  \texttt{title : EString} describe el título de una tarea y toma inicialmente
  el valor \texttt{Design landing page}.
  \item \texttt{Milestone} también hereda de \texttt{WorkItem}. Su atributo
  \texttt{name : EString} identifica el hito y tiene como valor inicial
  \texttt{First public release}.
  \item \texttt{TeamMember} es una clase concreta independiente. Su atributo
  \texttt{name : EString} usa \texttt{Alex} como valor predeterminado. La
  relación entre miembros y tareas se añadirá en un ejemplo posterior.
  \item El rombo negro de \texttt{Project.workItems} indica una referencia de
  contención: los objetos contenidos forman parte del ciclo de vida del
  proyecto. Su tipo es \texttt{WorkItem} y su multiplicidad \texttt{[1..6]}
  exige entre uno y seis elementos. Gracias a la herencia, esos elementos
  pueden ser instancias de \texttt{Task} o \texttt{Milestone}.
\end{itemize}

El fichero contiene además una anotación \texttt{blockly} con
\texttt{inputsInline=false} en cada clase. No modifica el dominio; es una pista
de presentación que solicita disponer los campos del bloque en filas. Se omite
en la clase gráfica para separar la estructura del dominio de su apariencia en
Blockly.

\subsubsection{El fichero \texttt{basicStructure.m2b}: un modelo textual del DSL}

La extensión \texttt{.m2b} pertenece al lenguaje textual definido por este
proyecto con Xtext. El DSL es la gramática
\path{Model2Blockly.xtext}; \path{basicStructure.m2b} es un modelo escrito de
acuerdo con esa gramática. Xtext analiza su sintaxis concreta y construye en
memoria un modelo semántico EMF cuya raíz es \texttt{DomainModel}
\cite{xtextProject,xtextGrammarLanguage}. El Listado
\ref{lst:basic-structure-m2b-completo} reproduce el fichero completo sin las
líneas en blanco.

\begin{lstlisting}[float=htbp, style=tfmm2b, caption={Contenido completo de \texttt{basicStructure.m2b}}, label={lst:basic-structure-m2b-completo}]
domain BasicStructure
class Project inputsInline false {
  attribute name : string [0..1] default "Website redesign"
  contains WorkItem workItems [1..6]
}
abstract class WorkItem inputsInline false {
}
class Task extends WorkItem inputsInline false {
  attribute title : string [0..1] default "Design landing page"
}
class Milestone extends WorkItem inputsInline false {
  attribute name : string [0..1] default "First public release"
}
class TeamMember inputsInline false {
  attribute name : string [0..1] default "Alex"
}
\end{lstlisting}

La lectura línea por línea es la siguiente:

\begin{description}
  \item[Línea 1.] \texttt{domain BasicStructure} crea el
  \texttt{DomainModel} raíz y fija el nombre usado en los artefactos generados.
  \item[Línea 2.] Declara la clase concreta \texttt{Project};
  \texttt{inputsInline false} solicita que sus entradas aparezcan en filas.
  \item[Línea 3.] Declara el atributo opcional \texttt{name}, de tipo textual,
  con multiplicidad \texttt{[0..1]} y valor predeterminado
  \texttt{Website redesign}.
  \item[Línea 4.] Declara que \texttt{Project} contiene, mediante la propiedad
  \texttt{workItems}, entre uno y seis objetos del tipo \texttt{WorkItem}.
  \item[Línea 5.] Cierra la definición de \texttt{Project}.
  \item[Línea 6.] Declara \texttt{WorkItem} como clase abstracta y mantiene la
  presentación vertical de sus posibles campos.
  \item[Línea 7.] Cierra su cuerpo vacío: en esta versión solo aporta el tipo
  común para la herencia y las conexiones.
  \item[Línea 8.] Declara la clase concreta \texttt{Task} y establece con
  \texttt{extends WorkItem} su relación de herencia.
  \item[Línea 9.] Añade el atributo textual opcional \texttt{title} y su valor
  predeterminado \texttt{Design landing page}.
  \item[Línea 10.] Cierra la definición de \texttt{Task}.
  \item[Línea 11.] Declara \texttt{Milestone} como otra subclase concreta de
  \texttt{WorkItem}.
  \item[Línea 12.] Añade su atributo textual opcional \texttt{name} y el valor
  inicial \texttt{First public release}.
  \item[Línea 13.] Cierra la definición de \texttt{Milestone}.
  \item[Línea 14.] Declara la clase concreta independiente
  \texttt{TeamMember}.
  \item[Línea 15.] Añade el nombre textual opcional del miembro y usa
  \texttt{Alex} como valor inicial.
  \item[Línea 16.] Cierra la definición de \texttt{TeamMember} y el fichero.
\end{description}

La correspondencia entre ambas representaciones es directa: un
\texttt{EClass} equivale a una declaración \texttt{class};
\texttt{abstract="true"} equivale a la palabra \texttt{abstract}; un
\texttt{EAttribute} de tipo \texttt{EString} equivale a
\texttt{attribute ... : string}; \texttt{eSuperTypes} equivale a
\texttt{extends}; y una \texttt{EReference} con
\texttt{containment="true"} equivale a \texttt{contains}. La multiplicidad y
los valores predeterminados se conservan en ambos casos. Así, los ficheros no
son idénticos en su sintaxis, pero sí describen la misma estructura semántica.

\subsubsection{Del modelo de entrada a las funciones del editor}

Al ejecutar el complemento, \texttt{GenerateBlocklyEditorHandler} selecciona
la rama según la extensión. La rama Ecore carga un \texttt{EPackage} y llama a
\texttt{EcoreAdapter}; la rama textual deja que Xtext construya un
\texttt{DomainModel} y llama a \texttt{DomainModelAdapter}. Los dos adaptadores
producen el mismo \texttt{EditorSpec}; después se valida, se serializa y recarga
como \path{BasicStructure_blocklyspec.xmi}, y finalmente
\texttt{BlocklyCodeGenerator} crea JavaScript, JSON y HTML.

La Figura \ref{fig:basic-structure-editor} muestra el resultado con el modelo de
ejemplo cargado. A la izquierda está el espacio de trabajo Blockly; a la derecha,
el inspector reconstruye el modelo de dominio a partir de los bloques.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\textwidth]{../../examples/feature_pairs/01_basic_structure/screenshots/editor_overview.png}
  \caption{Editor generado con \texttt{Project}, \texttt{Task} y
  \texttt{Milestone}, y el modelo equivalente mostrado en el inspector}
  \label{fig:basic-structure-editor}
\end{figure}

La primera correspondencia observable es \emph{clase concreta--bloque}. Los
adaptadores crean un \texttt{BlockTypeSpec} por cada clase y conservan la marca
de abstracción. El generador solo recorre \texttt{concreteBlockTypes}; por ello
genera bloques para \texttt{Project}, \texttt{Task}, \texttt{Milestone} y
\texttt{TeamMember}, pero no para \texttt{WorkItem}. Los atributos de tipo
\texttt{EString} o \texttt{string} se normalizan como campos \texttt{TEXT}; el
generador los emite como \texttt{field\_input} y copia su valor predeterminado.

La segunda correspondencia es \emph{contención--entrada de sentencias}. La
referencia \texttt{Project.}\allowbreak\texttt{workItems} y la instrucción equivalente
\texttt{contains WorkItem workItems [1..6]} se convierten en un
\texttt{StatementInput}\allowbreak\texttt{Spec} denominado \texttt{workItems}, cuyo
\texttt{checkType} es \texttt{WorkItem}. El Listado
\ref{lst:basic-structure-generated-block} muestra el fragmento resultante de
\path{BasicStructure_blocks.js}.

\begin{lstlisting}[float=htbp, style=tfmjavascript, caption={Definición Blockly generada para \texttt{Project}}, label={lst:basic-structure-generated-block}]
{
  "type": "Project",
  "message0": "Project",
  "message1": "name %1",
  "args1": [{"type": "field_input", "name": "name",
             "text": "Website redesign"}],
  "message2": "workItems %1",
  "args2": [{"type": "input_statement", "name": "workItems",
             "check": "WorkItem"}],
  "inputsInline": false
}
\end{lstlisting}

Las subclases \texttt{Task} y \texttt{Milestone} reciben conexiones anterior y
posterior tipadas como \texttt{WorkItem}; por eso encajan en la abertura
\texttt{workItems}. La herencia también organiza la paleta. Como muestra la
Figura \ref{fig:basic-structure-toolbox}, la categoría \texttt{WorkItem}
contiene los dos bloques concretos, mientras que la clase abstracta no aparece
como bloque arrastrable.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\textwidth]{../../examples/feature_pairs/01_basic_structure/screenshots/toolbox_inheritance.png}
  \caption{La categoría \texttt{WorkItem} ofrece las subclases concretas
  \texttt{Task} y \texttt{Milestone}}
  \label{fig:basic-structure-toolbox}
\end{figure}

La tercera correspondencia es \emph{multiplicidad--validación}. Los límites
\texttt{[1..6]} se copian al \texttt{StatementInputSpec}. Ambos adaptadores
crean después una regla \texttt{CARDINALITY}. Si se deja vacío
\texttt{Project.workItems}, el bloque muestra un aviso y la pestaña
\emph{Issues} informa del error, como se observa en la Figura
\ref{fig:basic-structure-cardinality}.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\textwidth]{../../examples/feature_pairs/01_basic_structure/screenshots/cardinality_validation.png}
  \caption{Validación generada al incumplir el límite inferior de
  \texttt{Project.workItems}}
  \label{fig:basic-structure-cardinality}
\end{figure}

El núcleo de estas decisiones se encuentra en los adaptadores y en el generador.
El Listado \ref{lst:basic-structure-adapter-core} resume las dos ramas que
normalizan atributos y contenciones; los nombres corresponden a los métodos
reales \texttt{convertEClass}, \texttt{convertAttribute} y
\texttt{convertContainment}.

\begin{lstlisting}[float=htbp, style=tfmjavaecore, caption={Núcleo de la normalización hacia \texttt{EditorSpec}}, label={lst:basic-structure-adapter-core}]
// EcoreAdapter: EAttribute -> FieldSpec
FieldSpec field = convertEAttribute(eAttr);
blockType.getFields().add(field);

// EcoreAdapter: containment EReference -> StatementInputSpec
StatementInputSpec input = new StatementInputSpec();
input.setName(eRef.getName());
input.setCheckType(eRef.getEReferenceType().getName());
input.setLowerBound(eRef.getLowerBound());
input.setUpperBound(eRef.getUpperBound());

// DomainModelAdapter: the textual model reaches the same types
FieldSpec field = convertAttribute((Attribute) feature);
StatementInputSpec input = convertContainment((Containment) feature);
\end{lstlisting}

Una vez construido \texttt{EditorSpec}, el código del Listado
\ref{lst:basic-structure-generator-core} filtra las clases abstractas y convierte
los dos tipos intermedios en los componentes Blockly observados en las figuras.

\begin{lstlisting}[float=htbp, style=tfmxtend, caption={Generación de bloques, campos y entradas de sentencias}, label={lst:basic-structure-generator-core}]
val blocks = spec.concreteBlockTypes.map[blockTypeToBlockJson(it)]

case TEXT:
  '''{"type": "field_input", "name": "«field.name»",
     "text": «toJsonString(field.defaultValue ?: "")»}'''

def String statementInputToArg(StatementInputSpec input) {
  val check = if (input.checkType !== null)
    '''"«input.checkType»"''' else "null"
  '''{"type": "input_statement", "name": "«input.name»",
     "check": «check»}'''
}
\end{lstlisting}

Los principales ficheros que intervienen en esta ejecución son:

\begin{itemize}
  \item \path{Model2Blockly.xtext}: define la sintaxis del DSL y el modelo que
  Xtext construye al leer un fichero \texttt{.m2b};
  \item \path{GenerateBlocklyEditorHandler.java}: carga el fichero seleccionado,
  elige el adaptador, valida el resultado y escribe el directorio generado;
  \item \path{EcoreAdapter.java}: transforma un \texttt{EPackage} en
  \texttt{EditorSpec};
  \item \path{DomainModelAdapter.java}: transforma el \texttt{DomainModel} del
  DSL en el mismo \texttt{EditorSpec};
  \item \path{BlocklySpecXmiSerializer.java}: materializa y recarga la frontera
  XMI intermedia;
  \item \path{BlocklyCodeGenerator.xtend}: genera las definiciones de bloques,
  la paleta, las validaciones, el modelo de ejemplo y las páginas HTML.
\end{itemize}

Con este resultado termina \texttt{01\_basic\_structure}. Los ejemplos
restantes conservarán este dominio como punto de partida y añadirán, de forma
progresiva, nuevos campos, composiciones, referencias, validaciones y generación
de código. Cada versión seguirá siendo autocontenida para poder ejecutarse y
compararse por separado.

En la rama Ecore, EMF carga el recurso y obtiene un \texttt{EPackage}; en la

se comprueba el modelo, se serializa como XMI, se vuelve a cargar y se valida de

ficheros relacionados y no solo la página autónoma mostrada en la sección
anterior. Las secciones posteriores detallan las operaciones resumidas en cada
caja de la figura.

\section{Carga y validación de las entradas}
\label{sec:carga-validacion-entradas}

La carga se implementa antes de los adaptadores. \texttt{EcoreAdapter} recibe un
objeto EMF ya construido y \texttt{DomainModelAdapter} recibe el modelo tipado
producido por Xtext; ninguna de las dos clases abre ficheros. En la ejecución
desde Eclipse, esta responsabilidad reside en
\texttt{GenerateBlocklyEditorHandler}; las clases de entrada independiente reproducen el mismo
patrón para ficheros situados fuera del espacio de trabajo. El resultado de esta etapa es
un \texttt{EPackage} o un \texttt{DomainModel} válido para iniciar la
transformación.

\subsection{Carga de un metamodelo \texttt{.ecore}}

El método \texttt{generateFromEcore} registra
\texttt{EcoreResourceFactoryImpl} para la extensión \texttt{ecore}, crea un
\texttt{ResourceSetImpl} y construye una URI de fichero a partir de la ubicación
del recurso seleccionado. La llamada \texttt{getResource(uri, true)} solicita la
carga inmediata del documento XMI y EMF resuelve sus elementos y referencias. El
primer objeto raíz se obtiene como \texttt{EPackage} y se entrega a
\texttt{EcoreAdapter}. La clase \texttt{EcoreToBlocklyMain} utiliza la misma
secuencia en su método \texttt{loadEPackage}.

Esta rama no utiliza el parser ni el validador de Xtext. Los problemas que
impiden leer el recurso se propagan como excepciones de carga; las restricciones
específicas que necesita el generador se comprueban después de la adaptación
mediante \texttt{BlocklySpecDiagnostics}. Esta separación evita interpretar
como sintaxis textual un metamodelo que ya dispone del formato estándar de EMF.

\subsection{Carga y validación de una entrada \texttt{.m2b}}

La ruta textual comienza registrando el lenguaje con
\texttt{Model2BlocklyStandalone}\allowbreak\texttt{Setup}. La configuración generada por Xtext
asocia el mismo lenguaje con las extensiones \texttt{.m2b} y
\texttt{.model2blockly}; la segunda se conserva por compatibilidad. El inyector
de Guice proporciona el \texttt{ResourceSet}, que carga el fichero como un
\texttt{XtextResource}. El parser crea el árbol EMF y el enlazador resuelve los
nombres usados para categorías, superclases y tipos. Si la carga termina
correctamente, el primer elemento del recurso debe ser una instancia de
\texttt{DomainModel}.

El Listado \ref{lst:carga-modelo-m2b} resume las llamadas Java que implementan
esta etapa en el manejador. La clase de entrada independiente
\texttt{Model2BlocklyToBlocklyMain} contiene la misma secuencia, cambiando
únicamente el origen de la ruta del fichero.

\begin{lstlisting}[style=tfmjava, captionpos=t, caption={Secuencia comentada de carga y validación de una entrada \texttt{.m2b}}, label={lst:carga-modelo-m2b}]
// Crea la configuracion independiente del DSL.
Injector injector = new Model2BlocklyStandaloneSetup()
    // Registra en EMF los elementos generados por Xtext.
    .createInjectorAndDoEMFRegistration();
// Obtiene un conjunto de recursos configurado por Guice.
ResourceSet resourceSet = injector.getInstance(ResourceSet.class);
// Carga la URI y ejecuta el parser y el enlazador.
Resource resource = resourceSet.getResource(fileUri, true);
// Conserva el tipo Xtext para acceder a sus servicios.
XtextResource xtext = (XtextResource) resource;

// Comprueba la correspondencia con la sintaxis concreta.
xtext.validateConcreteSyntax();
// Propaga los errores de sintaxis y de enlazado.
Model2BlocklyValidationDiagnostics.throwIfSyntaxErrors(
    // Identifica el origen y entrega los errores del recurso.
    sourceLabel, resource.getErrors());
// Propaga los errores de las reglas semanticas del DSL.
Model2BlocklyValidationDiagnostics.throwIfErrors(
    // Asocia los diagnosticos con el fichero de entrada.
    sourceLabel,
    // Obtiene el validador registrado para este lenguaje.
    xtext.getResourceServiceProvider().getResourceValidator()
        // Ejecuta todas las reglas @Check sobre el recurso.
        .validate(resource, CheckMode.ALL,
            // Indica que esta validacion no se cancela.
            CancelIndicator.NullImpl));

// Declara la raiz tipada del modelo textual.
DomainModel domain =
    // Recupera el primer objeto EMF producido por Xtext.
    (DomainModel) resource.getAllContents().next();
\end{lstlisting}

Las llamadas comentadas cubren dos grupos de problemas. La primera comprobación recoge
errores producidos durante el análisis y el enlazado; la segunda ejecuta las
reglas \texttt{@Check} de \texttt{Model2BlocklyValidator}. Estas reglas detectan,
entre otros casos, nombres de clase duplicados, cardinalidades incoherentes,
entradas de valor con un tipo no válido, widgets incompatibles, referencias a
campos inexistentes y expresiones de validación no soportadas. El método
\texttt{throwIfErrors} detiene la generación únicamente ante diagnósticos de
severidad \emph{error}; las advertencias permanecen visibles en el editor, pero
permiten continuar.

\subsection{Niveles de validación y comunicación de errores}

La implementación aplica tres niveles consecutivos. Primero se comprueba que el
recurso pueda cargarse y, en la ruta textual, que su sintaxis y sus referencias
sean correctas. Después se ejecutan las reglas semánticas específicas del DSL.
Finalmente, tras llamar al adaptador correspondiente,
\texttt{BlocklySpecDiagnostics.assertValid} comprueba las invariantes del
\texttt{EditorSpec} común. Esta última validación se repite después de serializar
y recargar el XMI, por lo que el generador solo recibe un modelo que ha superado
el contrato intermedio completo.

Cuando la ejecución se realiza en Eclipse, los errores semánticos y los
diagnósticos del modelo común se convierten en marcadores
\texttt{IMarker.PROBLEM} asociados al fichero y, cuando existe información de
origen, a su línea. El manejador vuelve a abrir la entrada y muestra un diálogo con
el resumen. En las entradas independientes, el mismo diagnóstico se escribe en la
salida de error y el proceso termina con un código distinto de cero. De este
modo, las dos formas de ejecución comparten las comprobaciones, aunque presentan
el resultado mediante interfaces diferentes.

\section{Ruta textual \texttt{.m2b} con Xtext}
\label{sec:implementacion-xtext}

La gramática Xtext define el lenguaje textual de entrada \texttt{.m2b} y
vincula sus reglas con los conceptos del metamodelo EMF asociado. A partir de
esta gramática, Xtext genera el parser y el soporte de edición
\cite{xtextProject,bettini2013xtext,bettini2015xsemantics}. Así, cada fichero
DSL puede tratarse como un modelo EMF. La raíz de ese modelo agrupa el nombre
del dominio, las opciones de generación, la configuración del espacio de trabajo, las
categorías, las clases y las restricciones.

Las clases del dominio se declaran con una construcción específica del DSL. Cada
clase puede ser abstracta, generar un bloque de salida, heredar de otra clase,
pertenecer a una categoría, definir color, etiqueta, tooltip, disposición en
línea y plantilla de código. Dentro de una clase se declaran cuatro tipos de
elementos: atributos, contenciones, referencias y entradas de valor. Esta
distinción en la gramática se corresponde con las formas principales en las que
Blockly representa información: campos, entradas de sentencias, desplegables de
referencia y conectores de valor.

El DSL también incluye opciones de interfaz. Con estas opciones se pueden indicar
widgets, etiquetas, textos de ayuda, grupos,
orden de presentación, campos de solo lectura, campos ocultos y campos usados
para mostrar referencias. Esta información no es necesaria para un editor
Blockly básico, pero permite enriquecer la salida generada sin escribir
JavaScript a mano. En la memoria se usa para explicar la correspondencia con
Ecore mediante ejemplos pequeños, sin confundir la notación textual con el
metamodelo que genera Xtext.

Los Listados \ref{lst:composition-inputs-dsl} y
\ref{lst:references-integrity-dsl} separan dos decisiones que antes aparecían
mezcladas. El primero muestra cómo se declaran la composición y las entradas de
valor; el segundo se limita a la identidad y a las referencias no contenidas.
Los comentarios \texttt{//} explican cada sentencia incluida. Las Figuras
\ref{fig:ecore-composition-acotado} y
\ref{fig:ecore-references-acotado}, presentadas en la sección del adaptador
Ecore, muestran las estructuras equivalentes.

\begin{lstlisting}[style=tfmm2b, captionpos=t, caption={Fragmento clave de \texttt{03\_composition\_inputs} comentado línea a línea}, label={lst:composition-inputs-dsl}]
// Nombra el dominio que se convertira en EditorSpec.
domain CompositionInputs
// Crea la categoria de los bloques estructurales.
category Composition colour 200
// Crea una categoria distinta para los bloques con salida.
category Expressions colour 230

// Declara Document como bloque raiz de la composicion.
class Document category Composition colour 200 inputsInline false {
  // Crea la entrada de sentencias sections para uno a cuatro Section.
  contains Section sections [1..4]
    // Muestra sections como ranura titulada Sections y en segundo lugar.
    widget slot uiLabel "Sections" order 2 variant default
// Cierra la declaracion del bloque Document.
}

// Declara el tipo comun Section sin crear un bloque instanciable.
abstract class Section category Composition colour 120 inputsInline false {
// Cierra el supertipo abstracto Section.
}

// Declara Paragraph como bloque concreto compatible con Section.
class Paragraph extends Section category Composition colour 120 inputsInline false {
  // Crea la entrada de valor content, tipada como TextExpression.
  value TextExpression content shadow TextLiteral
    // Presenta content como ranura de expresion con etiqueta Content.
    widget expression-slot uiLabel "Content" order 2 variant default
// Cierra la declaracion del bloque Paragraph.
}

// Declara el tipo abstracto que define la conexion de salida aceptada.
abstract output class TextExpression category Expressions colour 230 inputsInline false {
// Cierra el tipo abstracto TextExpression.
}

// Crea el bloque sombra concreto y le asigna la salida TextExpression.
output as TextExpression class TextLiteral extends TextExpression
  // Coloca el bloque concreto en la categoria Expressions.
  category Expressions colour 230 inputsInline false {
// Cierra la declaracion de TextLiteral; se omite su atributo textual.
}
\end{lstlisting}

En este fragmento, \texttt{sections} y \texttt{content} son nombres internos
de entradas Blockly, no variables Java. La construcción \texttt{contains}
produce una entrada de sentencias para apilar bloques; \texttt{value} produce
una entrada horizontal. \texttt{TextExpression} es el tipo de conexión
aceptado, mientras que \texttt{TextLiteral} es el bloque sombra que aparece por
defecto hasta que el usuario conecta otra expresión compatible.

\begin{lstlisting}[style=tfmm2b, captionpos=t, caption={Fragmento clave de \texttt{04\_references\_integrity} comentado línea a línea}, label={lst:references-integrity-dsl}]
// Nombra el dominio dedicado a identidad y referencias.

// Crea la categoria comun de los bloques del ejemplo.

  attribute cardId : string [1..1] default "card-1" modelId
  // Permite elegir hasta tres Link y declara source como extremo opuesto.
  reference Link outgoing [0..3] opposite source unique ordered
    // Genera para outgoing un selector actualizado desde el workspace.
    widget reference-select uiLabel "Outgoing links" order 3 variant default
    // Muestra linkId como texto de cada Link seleccionable.

// Cierra la declaracion de Card.
}

// Declara Link como segundo elemento concreto del flujo.
class Link extends Element category References colour 120 inputsInline false {
  // Usa linkId como identidad estable de cada enlace.
  attribute linkId : string [1..1] default "link-1" modelId
  // Exige una Card origen y la sincroniza con Card.outgoing.
  reference Card source [1..1] opposite outgoing required unique ordered

    referenceLabelField title
  // Exige entre una y dos tarjetas destino, permitiendo repeticiones.
  reference Card target [1..2] required nonUnique unordered
    // Representa target mediante otro selector de referencias.
    widget reference-select uiLabel "Target cards" order 4 variant default
    // Vuelve a usar title como etiqueta comprensible para el usuario.
    referenceLabelField title
// Cierra la declaracion de Link.
}
\end{lstlisting}

Aquí \texttt{cardId} y \texttt{linkId} son atributos del dominio marcados como
identificadores; permiten que el editor conserve una referencia aunque cambie
su etiqueta visible. \texttt{outgoing}, \texttt{source} y \texttt{target} son
nombres de referencias del modelo. \texttt{opposite} enlaza los dos extremos
que deben sincronizarse y \texttt{referenceLabelField} decide qué atributo
humano se muestra en el desplegable, sin sustituir el identificador persistido.

Una vez analizado el fichero como se explicó en la Sección
\ref{sec:carga-validacion-entradas}, el resultado de esta gramática es un
\texttt{DomainModel} enlazado y validado. Ese objeto constituye la entrada del
adaptador Java descrito posteriormente en la Sección
\ref{sec:implementacion-domainmodel-adapter}.

\section{Modelo intermedio EMF y vista Java}
\label{sec:implementacion-modelo-intermedio}

El contrato del modelo intermedio está definido como metamodelo EMF en el
fichero \texttt{blockly\_editor\_spec.ecore}, dentro del directorio
\texttt{model}. EMF genera a partir de él las interfaces Java
\texttt{EditorSpec}, \texttt{BlockTypeSpec}, \texttt{FieldSpec} y los demás
tipos del paquete \texttt{intermediate.blocklyspec}, junto con
\texttt{BlocklySpecFactory}. Para facilitar la construcción de esas instancias,
el proyecto conserva además \texttt{BlocklyEditorSpec}, una vista Java auxiliar del
mismo contenido. \texttt{BlocklySpecModelMapper} implementa la copia en ambos
sentidos entre esa vista y las instancias creadas por la factoría EMF.

El objeto EMF no se entrega directamente al generador después de la adaptación.
La serialización se encapsula en
\texttt{BlocklySpecXmi}\allowbreak\texttt{Serializer}. Esta clase crea un
\texttt{ResourceSet}\allowbreak\texttt{Impl} y registra
\texttt{BlocklySpecPackage.}\allowbreak\texttt{eNS\_URI} y añade el
\texttt{EditorSpec} a un \texttt{XMIResource}\allowbreak\texttt{Impl} con la
URI en memoria \texttt{memory:/}\allowbreak\texttt{blocklyspec.xmi}. El recurso se guarda en UTF-8, se vuelve a
cargar desde esa cadena y se comprueba que su raíz siga siendo un
\texttt{EditorSpec}. El Listado \ref{lst:ciclo-editor-spec-xmi} muestra cómo el
manejador aplica este ciclo en las dos rutas de entrada.

\begin{lstlisting}[float=htbp, style=tfmjava, captionpos=t, caption={Validación, serialización y recarga comentadas del modelo intermedio}, label={lst:ciclo-editor-spec-xmi}]
// Valida el modelo comun creado por el adaptador.
BlocklySpecDiagnostics.assertValid(intermediateModel, sourceLabel,
    // Permite relacionar cada error con el modelo de origen.
    sourceMapper);

// Declara la cadena que contendra el XMI intermedio.
String intermediateXmi =
    // Serializa EditorSpec como un recurso XMI en memoria.
    BlocklySpecXmiSerializer.toXmi(intermediateModel);
// Declara el modelo que se usara para generar el editor.
EditorSpec spec =
    // Recarga el XMI y comprueba que su raiz sea EditorSpec.
    BlocklySpecXmiSerializer.fromXmiToEditorSpec(intermediateXmi);

// Valida de nuevo el modelo despues de la recarga.
BlocklySpecDiagnostics.assertValid(
    // Identifica esta comprobacion como la del XMI intermedio.
    spec, sourceLabel + " intermediate XMI");
// Declara el mapa ordenado de ficheros generados.
Map<String, String> generated =
    // Transforma el EditorSpec validado en HTML y JavaScript.
    new BlocklyCodeGenerator().generate(spec);
\end{lstlisting}
\FloatBarrier

En el extracto, \texttt{sourceMapper} representa el mapeador creado por
\texttt{forEPackage} o \texttt{forDomainModel}, según la ruta. El primer
diagnóstico puede asociarse con elementos del modelo fuente mediante
\texttt{sourceMapper}; el segundo valida el objeto recargado. De este modo, un
error de serialización, una raíz incorrecta o la pérdida de un dato obligatorio
se detectan antes de generar texto. La misma cadena XMI se conserva después como
\path{intermediate/*_blocklyspec.xmi}, por lo que el artefacto inspeccionable es
exactamente el contenido usado para generar el editor.

Cada tipo de bloque guarda su forma de conexión: bloque raíz, bloque apilable,
bloque apilable tipado, bloque de valor o bloque de valor tipado. Esta
clasificación permite generar las conexiones visuales adecuadas sin mezclar
reglas específicas de Blockly con la lectura del dominio. La implementación
mantiene además listas separadas para campos, entradas de sentencias,
referencias y entradas de valor, lo que facilita generar cada tipo de elemento
con la construcción Blockly adecuada.

El modelo intermedio también conserva información de orden para las entradas de
un bloque. Esta decisión es relevante para la ruta Ecore: cuando las
características de una clase se leen desde el metamodelo, el orden
original de atributos y referencias puede influir en la legibilidad del bloque
generado. El generador usa esta lista cuando está disponible y, si no existe,
aplica un orden por defecto.

La ventaja de esta implementación es el desacoplamiento. Los adaptadores de
entrada producen una instancia conforme al mismo metamodelo intermedio, y los
generadores consumen su vista Java sin depender de cómo fue creada. Así, las
entradas y las salidas quedan separadas en el código, pero el contrato MDE sigue
siendo el metamodelo EMF y su serialización XMI.

\section{Adaptador desde Ecore}
\label{sec:implementacion-ecore-adapter}

\subsection{Puntos de entrada y normalización común}

Los dos adaptadores se implementan como clases Java ordinarias con métodos
estáticos; no se instancian ni contienen plantillas de generación. El Listado
\ref{lst:entrada-adaptadores-java} muestra sus puntos de entrada reales. Cada
método realiza primero una normalización hacia \texttt{BlocklyEditorSpec}, una
vista Java interna formada por listas y objetos tipados, y después invoca
\texttt{BlocklySpecModelMapper.toEmfSpec}. Este segundo paso usa
\texttt{BlocklySpecFactory.eINSTANCE} para crear el \texttt{EditorSpec} definido
por el metamodelo común y copiar recursivamente categorías, bloques, campos,
entradas, validaciones y opciones del espacio de trabajo. Por tanto, la vista Java es un
objeto auxiliar de construcción; el resultado contractual del adaptador es la
instancia EMF \texttt{EditorSpec}.

\begin{lstlisting}[float=htbp, style=tfmjavaecore, caption={Puntos de entrada Java de los dos adaptadores}, label={lst:entrada-adaptadores-java}]
// Declara el punto de entrada de EcoreAdapter.java.
public static EditorSpec toEditorSpec(EPackage pkg) {
    // Recorre el EPackage y convierte la vista Java al modelo EMF comun.
    return BlocklySpecModelMapper.toEmfSpec(fromEPackage(pkg));
// Finaliza la ruta de adaptacion Ecore.
}

// Declara el punto de entrada de DomainModelAdapter.java.
public static EditorSpec toEditorSpec(DomainModel domain) {
    // Recorre el DomainModel de Xtext y crea el mismo modelo EMF comun.
    return BlocklySpecModelMapper.toEmfSpec(fromDomainModel(domain));
// Finaliza la ruta de adaptacion textual.
}
\end{lstlisting}

En el primer método, \texttt{pkg} es el paquete Ecore cargado desde
un fichero \texttt{.ecore}. En el segundo, \texttt{domain} es el árbol del modelo
textual que Xtext ha construido al analizar su fichero \texttt{.m2b}. Ambos son
objetos de entrada; los dos métodos devuelven un \texttt{EditorSpec}, es decir,
el mismo tipo de modelo intermedio EMF aunque el origen sea diferente.

\subsection{Recorrido del paquete y conversión de clases}

En la ruta Ecore, \texttt{fromEPackage} recibe el objeto obtenido durante la
carga descrita en la Sección \ref{sec:carga-validacion-entradas}. El método copia
primero el nombre, \texttt{nsURI}, prefijo y opciones globales del paquete.
Después reúne los nombres de las clases que son destino de alguna referencia de
contención; este conjunto se usa más adelante para distinguir bloques raíz de
bloques que deben conectarse como hijos. A continuación recorre todos los
\texttt{EClassifier} del paquete y de sus subpaquetes, selecciona los
\texttt{EClass} y llama a \texttt{convertEClass}. Este proceso usa directamente
la API de EMF: clases, atributos, referencias, herencia y cardinalidades
\cite{emfOverview}.

El Listado \ref{lst:recorrido-eclass-ecore} conserva únicamente el bucle que
realiza el despacho de clases. Se omiten la lectura de las opciones globales y
la generación posterior de validaciones, ya que no intervienen en la decisión
mostrada. El fragmento pertenece al método \texttt{fromEPackage}; no es
pseudocódigo.

La dirección de los datos en este fragmento es
\texttt{eClass} $\rightarrow$ \texttt{bt} $\rightarrow$ \texttt{spec}: una clase
Ecore produce un descriptor de bloque y este se añade al descriptor del editor.
El argumento \texttt{categoryMap} es un mapa que asocia el nombre de cada
categoría con su \texttt{CategorySpec}; \texttt{containedTypeNames} es el conjunto
de nombres de clases que aparecen como destino de una contención. Este último
conjunto permite decidir posteriormente si una clase representa una raíz o un
elemento hijo.

\begin{lstlisting}[float=htbp, style=tfmjavaecore, captionpos=t, caption={Fragmento comentado del recorrido de clases Ecore}, label={lst:recorrido-eclass-ecore}]
// Recorre los clasificadores del paquete y de sus subpaquetes.
for (EClassifier classifier : allClassifiers(pkg)) {
    // Conserva solo los clasificadores que representan clases Ecore.
    if (classifier instanceof EClass) {
        // Recupera la clase con el tipo ofrecido por la API de EMF.
        EClass eClass = (EClass) classifier;
        // Crea bt, el descriptor de bloque obtenido desde eClass.
        BlockTypeSpec bt = convertEClass(
            // Entrega la clase, las categorias y los tipos contenidos.
            eClass, categoryMap, containedTypeNames);
        // Incorpora bt en spec, el editor intermedio en construccion.
        spec.getBlockTypes().add(bt);
    // Finaliza el tratamiento del EClass actual.
    }
// Finaliza el recorrido de clasificadores.
}
\end{lstlisting}
\FloatBarrier

Aplicado a la Figura \ref{fig:basic-structure-ecore}, el bucle invoca
\texttt{convertEClass} para \texttt{Project}, \texttt{WorkItem}, \texttt{Task},
\texttt{Milestone} y \texttt{TeamMember}. Cada invocación crea un
\texttt{BlockTypeSpec}.
La propiedad \texttt{isAbstract} de \texttt{WorkItem} se copia al descriptor,
por lo que este tipo participa en la comprobación de conexiones, pero no se
ofrece como bloque instanciable en la paleta.

Desde el punto de vista de MDE, este adaptador es una transformación de modelos
implementada en Java sobre la API de EMF. No se ha usado un lenguaje específico
de transformación como ATL o ETL. La razón es pragmática: el generador debe
integrarse dentro de un complemento Eclipse/Xtext, reutilizar utilidades Java del
proyecto, emitir diagnósticos concretos sobre el fichero de entrada y construir
la instancia EMF \texttt{EditorSpec} que después se serializa como XMI. La
implementación queda así dentro de la misma cadena Java que carga el recurso y
comunica los errores al entorno Eclipse. La Tabla
\ref{tab:transformacion-ecore-editor-spec} resume las reglas principales de la
transformación.

\subsection{Conversión de atributos y enumerados}

Cada atributo editable se procesa durante el recorrido de la clase. El método
\texttt{convert}\allowbreak\texttt{EAttribute} crea un \texttt{FieldSpec} y
selecciona su representación visual a partir del \texttt{EDataType}. El Listado
\ref{lst:conversion-eattribute} incluye la rama de texto utilizada por
\texttt{01\_basic\_structure} y anticipa las ramas de enumeración y booleano que
se incorporan en el ejemplo siguiente. Los casos numéricos, de color, ángulo e
imagen se omiten porque siguen el mismo patrón.

En el código, \texttt{eAttr} es el atributo Ecore recibido por
\texttt{convertEAttribute}; \texttt{fs} es el \texttt{FieldSpec} de salida,
creado al comienzo del método; \texttt{type} conserva el tipo de datos de
\texttt{eAttr}; y \texttt{lit} representa el literal de enumerado procesado en
cada iteración. La dirección de la conversión es
\texttt{eAttr} $\rightarrow$ \texttt{fs}; posteriormente, \texttt{fs} se añade
a la lista de campos de \texttt{bt}. El fragmento comienza después de crear
\texttt{fs}; por ello esa inicialización no se repite en el listado.

\newpage
\begin{lstlisting}[style=tfmjavaecore, captionpos=t, caption={Fragmento comentado de la conversión de atributos Ecore}, label={lst:conversion-eattribute}]
// eAttr es el atributo de entrada; type conserva su EDataType.
EDataType type = eAttr.getEAttributeType();
// Comprueba si el atributo utiliza un enumerado del dominio.
if (type instanceof EEnum) {
    // eEnum es el tipo enumerado asociado a eAttr.
    EEnum eEnum = (EEnum) type;
    // fs es el campo de salida; lo configura como desplegable.
    fs.setFieldType(FieldSpec.FieldType.DROPDOWN);
    // lit es el literal procesado en esta iteracion.
    for (EEnumLiteral lit : eEnum.getELiterals()) {
        // Anade a fs una opcion con el nombre y el valor de lit.
        fs.getOptions().add(new DropdownOption(
            lit.getName(), lit.getLiteral()));
    }
// Trata los tipos de datos que no son enumerados.
} else {
    // Selecciona la representacion de fs con el nombre de type.
    switch (type.getName()) {
        // Convierte las cadenas en campos de texto.
        case "EString":
            // Configura fs como campo de texto.
            fs.setFieldType(FieldSpec.FieldType.TEXT); break;
        // Los casos numericos se omiten en este fragmento.
        // Convierte los valores logicos en casillas booleanas.
        case "EBoolean":
            // Configura fs como campo booleano.
            fs.setFieldType(FieldSpec.FieldType.BOOLEAN); break;
    }
}
\end{lstlisting}

En el primer ejemplo, esta decisión convierte en campos de texto los atributos
\texttt{Project.name}, \texttt{Task.title}, \texttt{Milestone.name} y
\texttt{TeamMember.name}, todos de tipo \texttt{EString}. La Figura
\ref{fig:basic-structure-editor} permite observar los tres primeros en el modelo
cargado. Después de seleccionar el tipo de campo, el mismo método copia el valor
predeterminado y marca el campo como obligatorio cuando \texttt{lowerBound} es
mayor o igual que uno.

\subsection{Conversión de contenciones y referencias}

El tratamiento de una \texttt{EReference} depende de su función. La anotación
\texttt{input\_value} genera una conexión horizontal; una referencia con
\texttt{containment=true}, una entrada estructural; y las restantes, selectores
dinámicos. El Listado \ref{lst:conversion-containment-ecore} conserva solo la
rama usada por \texttt{Project.workItems}; omite las alternativas que no modifican
esta creación estructural.

En el fragmento, \texttt{eRef} es la \texttt{EReference} de entrada y
\texttt{refAnn}, su \texttt{EAnnotation} Blockly opcional. \texttt{bt} es el
\texttt{BlockTypeSpec} de la clase propietaria y \texttt{sis}, la
\texttt{Statement}\allowbreak\texttt{InputSpec} de salida. \texttt{check} guarda
el tipo aceptado por la conexión; \texttt{hasContainments} recuerda que el
bloque contiene hijos. El flujo es
\texttt{eRef} $\rightarrow$ \texttt{sis} $\rightarrow$ \texttt{bt}.

\begin{lstlisting}[style=tfmjavaecore, captionpos=t, caption={Fragmento comentado de la conversión de una contención Ecore}, label={lst:conversion-containment-ecore}]
// eRef es la referencia actual; selecciona su rama de contencion.
if (eRef.isContainment()) {
    // hasContainments recuerda que bt contiene elementos hijos.
    hasContainments = true;
    // Crea sis, la entrada estructural producida desde eRef.
    StatementInputSpec sis = new StatementInputSpec();
    // Copia en sis el nombre de eRef.
    sis.setName(eRef.getName());
    // refAnn es la anotacion opcional; obtiene su tipo check.
    String check = refAnn != null
        // Lee el valor check de la anotacion Blockly.
        ? refAnn.getDetails().get("check") : null;
    // Configura en sis el tipo explicito o el EClass de eRef.
    sis.setCheckType(check != null && !check.isBlank()
        // Conserva el tipo indicado mediante la anotacion.
        ? check
        // Infiere el tipo a partir del EClass contenido.
        : eRef.getEReferenceType().getName());
    // Copia en sis el numero minimo admitido por eRef.
    sis.setLowerBound(eRef.getLowerBound());
    // Copia en sis el maximo de eRef y normaliza el limite abierto.
    sis.setUpperBound(eRef.getUpperBound() == -1
        // Representa el limite abierto mediante cero en el modelo comun.
        ? 0 : eRef.getUpperBound());
    // Incorpora sis al descriptor de bloque bt.
    bt.getStatementInputs().add(sis);
// Finaliza la conversion de la contencion.
}
\end{lstlisting}

Para \texttt{Project.workItems}, el adaptador crea por tanto una
\texttt{StatementInputSpec} denominada \texttt{workItems}, con tipo aceptado
\texttt{WorkItem}, límite inferior uno y límite superior seis. La herencia
permite que los bloques \texttt{Task} y \texttt{Milestone} satisfagan ese tipo.
Las cardinalidades se usan además para generar reglas de validación, de modo que
el editor avisa si el proyecto contiene menos de uno o más de seis elementos.

\subsection{Inferencia de conexiones y herencia}

La inferencia de conexiones también se realiza en el adaptador. Las clases
contenedoras que no están contenidas por otras pueden convertirse en bloques
raíz sin conexión vertical. Las clases que heredan de una superclase pueden
generar conexiones tipadas. Las clases marcadas como bloques de salida generan
conectores de valor. Esta inferencia es importante porque evita que el usuario
tenga que escribir a mano reglas de conexión Blockly para cada clase. En el
primer ejemplo, \texttt{Project} se reconoce como raíz, mientras que
\texttt{Task} y \texttt{Milestone} reciben conexiones compatibles con
\texttt{WorkItem}.

\section{Adaptador desde la ruta textual \texttt{.m2b}}
\label{sec:implementacion-domainmodel-adapter}

El adaptador de la ruta textual también está implementado manualmente en Java.
\texttt{DomainModelAdapter.fromDomainModel} recibe la raíz EMF producida por
Xtext y ejecuta, en orden, los métodos \texttt{convertCategories},
\texttt{convertClasses}, \texttt{convertValidations} y
\texttt{convertConstraints}. Después genera las validaciones inferidas de
cardinalidad, obligatoriedad y unicidad, y finalmente copia las opciones del
espacio de trabajo con \texttt{convertWorkspace}\allowbreak\texttt{Options}. El objeto Java resultante vuelve
al método \texttt{toEditorSpec} del Listado
\ref{lst:entrada-adaptadores-java}, donde se convierte al mismo modelo EMF común
que en la ruta Ecore.

El mapeo es más directo que en Ecore porque la gramática ya distingue los
conceptos específicos que necesita Model2Blockly. Los atributos se convierten en
campos, las contenciones en entradas estructurales, las referencias en
desplegables dinámicos y las entradas de valor en conexiones horizontales. Las
restricciones de orden se convierten en validaciones, y los campos marcados como
obligatorios generan comprobaciones de obligatoriedad.

La conversión de cada clase se implementa con un recorrido de la lista
\texttt{Feature} generada por Xtext. El Listado
\ref{lst:despacho-domainmodel-adapter} muestra el despacho esencial. Cada tipo
concreto se entrega a un método especializado y el nombre de la entrada se añade
a \texttt{orderedInputNames}; de este modo, el orden escrito en el fichero
\texttt{.m2b} se conserva al construir el bloque.

\begin{lstlisting}[style=tfmjava, captionpos=t, caption={Despacho comentado de elementos del DSL en \texttt{DomainModelAdapter}}, label={lst:despacho-domainmodel-adapter}]
// Recorre en orden las caracteristicas de la clase del DSL.
for (Feature feature : cls.getFeatures()) {
    // Distingue los atributos editables.
    if (feature instanceof Attribute) {
        // Convierte el atributo en un campo del modelo comun.
        FieldSpec field = convertAttribute((Attribute) feature);
        // Incorpora el campo al tipo de bloque.
        bt.getFields().add(field);
        // Conserva la posicion declarada en el fichero .m2b.
        bt.getOrderedInputNames().add(field.getName());
    // Distingue las relaciones jerarquicas de contencion.
    } else if (feature instanceof Containment) {
        // Declara la entrada estructural resultante.
        StatementInputSpec input =
            // Copia tipo, cardinalidad y metadatos de interfaz.
            convertContainment((Containment) feature);
        // Incorpora la entrada de sentencias al bloque.
        bt.getStatementInputs().add(input);
        // Conserva su posicion respecto de las demas entradas.
        bt.getOrderedInputNames().add(input.getName());
    // Distingue las referencias a objetos existentes.
    } else if (feature instanceof Reference) {
        // Declara el desplegable de referencia resultante.
        ReferenceFieldSpec reference =
            // Copia el destino, obligatoriedad y presentacion.
            convertReference((Reference) feature);
        // Incorpora la referencia al tipo de bloque.
        bt.getReferenceFields().add(reference);
        // Conserva tambien su posicion visual.
        bt.getOrderedInputNames().add(reference.getName());
    // Distingue las conexiones horizontales de valor.
    } else if (feature instanceof ValueInput) {
        // Convierte el tipo aceptado y el posible bloque sombra.
        ValueInputSpec input = convertValueInput((ValueInput) feature);
        // Incorpora la entrada de valor al bloque.
        bt.getValueInputs().add(input);
        // Registra su nombre en el orden comun.
        bt.getOrderedInputNames().add(input.getName());
    // Finaliza la alternativa aplicada a la caracteristica.
    }
// Finaliza el recorrido de la clase.
}
\end{lstlisting}

La implementación usa también información de herencia para determinar la forma
de conexión. Una clase marcada como bloque de salida se convierte en bloque de
valor; una clase con superclase genera conexiones tipadas; una clase con
contenciones y sin superclase puede funcionar como bloque raíz; y una clase
ordinaria se genera como bloque apilable. De este modo, la semántica declarada
en la sintaxis textual se transforma en reglas visuales de Blockly sin que el
autor del dominio tenga que conocer la API de bajo nivel de la biblioteca.

La estructura principal se lee con los tipos Java generados por Xtext
(\texttt{ClassDef}, \texttt{Attribute}, \texttt{Containment},
\texttt{Reference} y \texttt{ValueInput}). Solo algunas opciones de interfaz,
código y espacio de trabajo se obtienen mediante reflexión: \texttt{eClass()}
localiza la característica con \texttt{getEStructuralFeature} y \texttt{eGet}
recupera su valor. Esta decisión permite
que metadatos añadidos recientemente a la gramática puedan leerse antes de
regenerar todos los accesores, sin renunciar a la comprobación estática en el
recorrido estructural que determina los bloques.

\section{Generador HTML/JavaScript}
\label{sec:implementacion-generador-html}

El generador de la salida HTML/JavaScript transforma el modelo intermedio en los
artefactos necesarios para abrir el editor en un navegador: bloques, paleta,
exportación, validaciones, página de edición, página autónoma, espacio de trabajo de
validaciones, modelo de ejemplo e informe de generación. Esta salida usa Blockly
para definir bloques, inyectar el espacio de trabajo, gestionar la paleta, serializar y
generar código \cite{blocklyDocs}.

La generación de código se implementa principalmente en Xtend. La clase
principal, \texttt{Blockly\allowbreak{}Code\allowbreak{}Generator.xtend}, recibe
un \texttt{EditorSpec} y produce un mapa ordenado de nombres de fichero a
contenido textual. El Listado \ref{lst:entrada-generador-xtend} reproduce el
método de entrada: cada función \texttt{generate*} devuelve una cadena y el mapa
conserva la relación entre esa cadena y su fichero de destino.

\begin{lstlisting}[style=tfmxtend, captionpos=t, caption={Método de entrada de \texttt{BlocklyCodeGenerator.xtend} comentado línea a línea}, label={lst:entrada-generador-xtend}]
// Declara la operacion que recibe el modelo intermedio comun.
def Map<String, String> generate(EditorSpec spec) {
    // Crea un mapa que conserva el orden de los artefactos.
    val files = new LinkedHashMap<String, String>()
    // Obtiene el nombre base o usa domain si no esta definido.
    val base = spec.domainName ?: "domain"
    // Genera las definiciones JSON de los bloques.
    files.put(base + "_blocks.js", generateBlocksJs(spec))
    // Genera la paleta y sus categorias.
    files.put(base + "_toolbox.js", generateToolboxJs(spec))
    // Genera las funciones de exportacion de cada bloque.
    files.put(base + "_generators.js", generateGeneratorsJs(spec))
    // Genera las reglas de validacion del espacio de trabajo.
    files.put(base + "_validations.js", generateValidationsJs(spec))
    // Genera la pagina modular del editor.
    files.put(base + "_editor.html", generateEditorHtml(spec))
    // Genera la pagina autonoma de demostracion.
    files.put(base + "_standalone.html", generateStandaloneHtml(spec))
    // Registra la pagina para editar reglas visualmente.
    files.put("validation_workspace.html",
        // Delega su contenido en el generador especializado.
        ValidationWorkspaceHtmlGenerator.generate(spec))
    // Registra la representacion serializada de las reglas.
    files.put("validation_blocks.json",
        // Convierte las validaciones en arboles de bloques.
        ValidationBlockModelGenerator.generate(spec))
    // Registra el evaluador JavaScript de esos arboles.
    files.put("validation_runtime.js",
        // Emite JavaScript clasico compatible con el navegador.
        ValidationRuntimeGenerator.generateClassicJs(spec))
    // Genera un modelo inicial para probar el editor.
    files.put("sample_model.json", SampleModelGenerator.generate(spec))
    // Devuelve rutas y contenidos sin escribir todavia en disco.
    return files
// Finaliza la operacion principal del generador.
}
\end{lstlisting}

Xtend se usa como mecanismo de generación porque se integra bien con Xtext y
permite escribir plantillas de
texto legibles dentro del proyecto Eclipse. No se ha usado Acceleo ni un motor
externo de plantillas. Algunas piezas auxiliares, como el modelo de ejemplo, el
entorno de ejecución de las validaciones y la vista visual de reglas, se implementan en clases
Java separadas para mantener responsabilidades acotadas.

El mapa no escribe directamente en disco. El
\texttt{GenerateBlocklyEditorHandler} antepone \texttt{html/} a sus rutas y
añade tres resultados producidos fuera de Xtend: el XMI intermedio, el
\texttt{README.md} y el informe de generación. Finalmente,
\texttt{writeFiles} crea los \texttt{IFile} del espacio de trabajo y actualiza el proyecto.
Esta separación permite reutilizar el mismo generador desde las entradas
independientes sin depender de la API de Eclipse.

El informe se construye mediante
\texttt{GenerationReport}\allowbreak\texttt{HtmlRenderer}. Esta clase recibe la
fuente, el \texttt{EditorSpec} y el inventario de artefactos, y produce
\texttt{generation\_}\allowbreak\texttt{report.html}. El \texttt{README.md} se
compone en el manejador o en la entrada independiente correspondiente, ya que
incluye instrucciones adaptadas al modo de ejecución. Ambos resultados se
añaden al mapa antes de escribirlo, pero no forman parte de la salida directa de
\texttt{BlocklyCodeGenerator}.

La generación de bloques comienza en \texttt{generateBlocksArray}, que filtra
los tipos concretos y llama a \texttt{blockTypeToBlockJson}. Este método crea
mapas de campos, referencias y entradas, y recorre
\texttt{orderedInputNames} para conservar el orden establecido por el
adaptador. Cada elemento se delega en \texttt{fieldToArg},
\texttt{referenceToArg}, \texttt{valueInputToArg} o
\texttt{statementInput}\allowbreak\texttt{ToArg}. Finalmente, un
\texttt{switch} sobre \texttt{Connection}\allowbreak\texttt{Type} emite
\texttt{previous}\allowbreak\texttt{Statement},
\texttt{nextStatement} u \texttt{output} con tipo libre o tipado. Las clases
abstractas quedan en el modelo para resolver herencia y conexiones, pero no se
incluyen como bloques instanciables.

La generación de la paleta produce el conjunto de bloques disponible para el
usuario. Si no hay categorías, el generador puede emitir una paleta simple. Si
existen categorías, genera una paleta categorizada, incluyendo subcategorías cuando se
han definido. También se incluyen categorías integradas de Blockly, como lógica,
bucles, matemáticas, variables y funciones, para que los dominios puedan
combinar bloques propios con construcciones generales cuando sea necesario.

\texttt{BlockTypeSpec} que se está generando, \texttt{rowMessages} contiene una
etiqueta por campo y \texttt{rowArgs} contiene el fragmento JSON del control
correspondiente. \texttt{messageIndex} empieza en uno porque
\texttt{message0} se reserva para el título del bloque.

\begin{lstlisting}[float=htbp, style=tfmxtend, captionpos=t, caption={Generación comentada de una fila por campo cuando \texttt{inputsInline=false}}, label={lst:filas-campos-blockly}]
// Decide si bt debe presentar cada entrada en una fila independiente.
val useStackedRows = bt.message0 === null
    && Boolean.FALSE.equals(bt.inputsInline) && !rowArgs.empty
// Genera la rama vertical solo cuando se cumple esa condicion.
val messageJson = if (useStackedRows) {
    // rows acumula las propiedades messageN y argsN del JSON.
    val rows = new ArrayList<String>()
    // Reserva message0 para la etiqueta principal del bloque bt.
    rows.add('''"message0": «toJsonString(bt.label ?: bt.typeName)»,
        "args0": [],''')
    // rowIndex identifica la entrada que se va a convertir.
    var rowIndex = 0
    // Recorre en paralelo las etiquetas y los argumentos preparados.
    while (rowIndex < rowArgs.size) {
        // Blockly numera la primera fila de campos como message1.
        val messageIndex = rowIndex + 1
        // Anade la etiqueta visible y el unico control de esta fila.
        rows.add('''"message«messageIndex»":
            «toJsonString(rowMessages.get(rowIndex))»,
            "args«messageIndex»": [«rowArgs.get(rowIndex)»],''')
        // Avanza hasta la siguiente entrada de bt.
        rowIndex++
    }
    // Une las propiedades para insertarlas en la definicion del bloque.
    rows.join("\n")
}
\end{lstlisting}

Si existe un \texttt{message0} explícito, como en \texttt{VisualFields}, el
generador lo respeta y mantiene la composición declarada por el autor. En este
caso, el mensaje enumera \texttt{colour}, \texttt{angle}, \texttt{image} y
\texttt{label} en el mismo orden que los atributos, sin introducir una segunda
nomenclatura de presentación. Así, la misma implementación permite un
formulario legible en varias filas y, a la vez, un bloque visual compacto cuando
el dominio controla expresamente su mensaje.

\begin{lstlisting}[float=htbp, style=tfmjavascript, captionpos=t, caption={Expansión comentada de una secuencia de sentencias}, label={lst:render-domain-statements}]
// Recibe block, el bloque propietario, e inputName, su entrada de sentencias.
function renderDomainStatement(block, inputName) {
    // Obtiene el primer bloque conectado a la entrada indicada.
    var child = block.getInputTargetBlock(inputName);
    // Crea lines para conservar cada fragmento en orden.
    var lines = [];
    // Recorre la cadena mientras exista un comando conectado.
    while (child) {
        // Aplica a child la plantilla asociada con su tipo de bloque.
        var rendered = renderDomainBlock(child);
        // Conserva solamente los fragmentos que no estan vacios.
        if (rendered) lines.push(rendered);
        // Avanza al siguiente comando de la misma secuencia Blockly.
        child = child.getNextBlock();
    // Finaliza el recorrido de la entrada de sentencias.
    }
    // Une los fragmentos con saltos de linea para sustituir el marcador.
    return lines.join('\n');
// Finaliza la expansion de inputName.
}
\end{lstlisting}

\texttt{applyDomainTemplate} reconoce tres familias de marcadores: campos
simples como \texttt{\{\{name\}\}}, el tipo del bloque mediante
\texttt{\{\{type\}\}} y entradas estructurales como
\texttt{\{\{value:x\}\}} o \texttt{\{\{statements:x\}\}}. Si falta una
plantilla, \texttt{renderFallbackDomainBlock} conserva una representación
textual genérica, de modo que la exportación continúa disponible durante el
desarrollo del dominio.

La pestaña \emph{Code} reutiliza \texttt{generateDomainCode(workspace)} en
\texttt{updateOutput}; escribe el resultado con \texttt{textContent}, sin
ejecutarlo, y lo actualiza después de cada cambio. La opción
\emph{Export Code} llama a la misma función y utiliza
\texttt{codeFileExtension} para nombrar la descarga. La prueba del ejemplo
carga el modelo en ambas páginas, comprueba las cuatro plantillas, el lenguaje,
la extensión y los 60 caracteres generados, y guarda el mismo resultado como
\path{html/sample_generated.js} dentro de cada carpeta de salida.

// Decide si feature debe producir un control editable en Blockly.
private static boolean isEditableFeature(EStructuralFeature feature) {
    // Excluye un valor calculado a partir de otras propiedades.
    return !feature.isDerived()
        // Excluye un valor que Ecore no serializa de forma persistente.
        && !feature.isTransient()
        // Excluye un valor que Ecore tampoco almacena en la instancia.
        && !feature.isVolatile()
        // Conserva solamente los rasgos que el usuario puede modificar.
        && feature.isChangeable();
// Finaliza la decision para el rasgo actual.
}

// Reune los clasificadores de pkg y de todos sus descendientes.
private static List<EClassifier> allClassifiers(EPackage pkg) {
    // Crea result, la lista comun que recibira cada clasificador.
    List<EClassifier> result = new ArrayList<>();
    // Inicia el recorrido recursivo en el paquete recibido.
    collectClassifiers(pkg, result);
    // Devuelve la lista completa al proceso de conversion.
    return result;
// Finaliza la preparacion del recorrido.
}

// Visita pkg y anade sus clasificadores a result.
private static void collectClassifiers(EPackage pkg,
        List<EClassifier> result) {
    // Detiene la recursion si no existe un paquete que visitar.
    if (pkg == null) return;
    // Incorpora las clases y tipos declarados directamente en pkg.
    result.addAll(pkg.getEClassifiers());
    // Recorre cada subpaquete directo del paquete actual.
    for (EPackage sub : pkg.getESubpackages()) {
        // Aplica el mismo proceso a sub sin crear otro acumulador.
        collectClassifiers(sub, result);
    // Finaliza el recorrido de los subpaquetes directos.
    }
// Finaliza la visita del paquete actual.
}
\end{lstlisting}

\section{Validaciones y referencias en tiempo de ejecución}
\label{sec:implementacion-validaciones-referencias}

Los ejemplos 04 y 05 han mostrado el resultado observable de las referencias y
de los diagnósticos. Esta sección no repite esos casos, sino que explica los
mecanismos JavaScript comunes que los mantienen durante la edición. La
implementación distingue entre validación estática del DSL, realizada por
Eclipse/Xtext antes de generar, y validación del modelo construido, ejecutada
en el navegador sobre el espacio de trabajo Blockly.

\subsection{Compilación y presentación de las reglas}

\texttt{generateValidationsJs} produce las funciones
\texttt{computeValidation}\allowbreak\texttt{Warnings},
\texttt{applyValidation}\allowbreak\texttt{Warnings} e
\texttt{init}\allowbreak\texttt{Validations}. La primera recorre
\texttt{workspace.}\allowbreak\texttt{getAllBlocks(false)} y evalúa las reglas
aplicables a cada tipo. Primero intenta ejecutar el modelo visual activo si
todas sus reglas poseen una expresión traducible. Si no existe ese modelo o
alguna regla no puede ejecutarse, utiliza las comprobaciones emitidas
directamente desde \texttt{EditorSpec}. Las reglas de orden consultan
\texttt{getPreviousBlock}; las de cardinalidad siguen la cadena iniciada en
\texttt{getInputTargetBlock}; y las de obligatoriedad y unicidad leen y
comparan los valores de campo. \texttt{initValidations} registra un listener
específico que repite el cálculo después de crear, borrar, mover o modificar un
bloque.

Las reglas se representan también como árboles en
\texttt{validation\_blocks.json}. La clase Java
\texttt{ValidationRuntimeGenerator} transforma cada árbol en una expresión para el
entorno de ejecución y genera \texttt{validation\_runtime.js}. En el navegador,
\texttt{createValidationAccessors} ofrece operaciones acotadas como
\texttt{value}, \texttt{has}, \texttt{inputCount}, \texttt{fieldUnique} y
\texttt{previousBlockIs}; \texttt{evaluateRuntimeExpression} ejecuta la
expresión con esos accesores. Esta representación permite que
\texttt{validation\_}\allowbreak\texttt{workspace.html} muestre las mismas reglas que utiliza el
editor, en lugar de mantener una segunda definición visual independiente.

El Listado \ref{lst:apply-validation-warnings} muestra el paso que convierte el
resultado del cálculo en información visible. \texttt{workspace} es el espacio
Blockly activo; \texttt{b} representa el bloque que se está limpiando;
\texttt{w} es un aviso con bloque, identificador y mensaje;
\texttt{pending} agrupa esos avisos por identificador; \texttt{k} es el
identificador que se está recorriendo; y \texttt{p} es el grupo asociado. El
agrupamiento es necesario porque un mismo bloque puede incumplir varias reglas,
pero Blockly expone un único texto de advertencia por bloque.

\begin{lstlisting}[style=tfmjavascript, caption={Presentación de los avisos de validación comentada línea a línea}, label={lst:apply-validation-warnings}]
// Recibe workspace, el espacio Blockly que debe volver a validarse.
function applyValidationWarnings(workspace) {
    // Devuelve una lista vacia si todavia no existe el espacio de trabajo.
    if (!workspace) return [];
    // Recorre todos los bloques antes de calcular el nuevo estado.
    workspace.getAllBlocks(false).forEach(function(b) {
        // Elimina de b cualquier advertencia procedente del calculo anterior.
        b.setWarningText(null);
    // Finaliza la limpieza del bloque actual.
    });
    // Ejecuta las reglas y guarda cada incumplimiento en warnings.
    var warnings = computeValidationWarnings(workspace);
    // Crea pending para agrupar los mensajes que pertenecen al mismo bloque.
    var pending = {};
    // Recorre cada aviso w producido por las reglas.
    warnings.forEach(function(w) {
        // Descarta un aviso que no pueda asociarse con un bloque visible.
        if (!w.block) return;
        // Crea el grupo del bloque la primera vez que aparece su identificador.
        if (!pending[w.block.id])
            // Conserva el bloque y una lista inicialmente vacia de mensajes.
            pending[w.block.id] = { b: w.block, msgs: [] };
        // Incorpora el mensaje actual al grupo de su bloque.
        pending[w.block.id].msgs.push(w.message);
    // Finaliza el agrupamiento del aviso actual.
    });
    // Recorre cada identificador k que posee mensajes pendientes.
    Object.keys(pending).forEach(function(k) {
        // Obtiene p, el bloque y sus mensajes ya agrupados.
        var p = pending[k];
        // Muestra todos los mensajes juntos en la advertencia del bloque.
        p.b.setWarningText(p.msgs.join('\n'));
    // Finaliza la actualizacion del bloque asociado con k.
    });
    // Reconstruye la pestaña Issues con la lista completa de avisos.
    renderValidationIssues(warnings);
    // Devuelve los avisos para que la exportacion pueda decidir si continua.
    return warnings;
// Finaliza la presentacion del nuevo resultado de validacion.
}
\end{lstlisting}

\subsection{Referencias dinámicas y referencias opuestas}

Las referencias no contenidas se implementan como campos cuyos valores son
identificadores de bloques. La función generada
\texttt{updateReferenceDropdowns} agrupa las instancias existentes por tipo,
construye para cada destino una pareja etiqueta--identificador y sustituye las
opciones del desplegable. La etiqueta se toma del
\texttt{referenceLabelField}, del campo \texttt{name} o, como último recurso,
del tipo y una parte del identificador. Si se elimina el bloque referenciado, el
valor deja de estar entre las opciones válidas y se limpia.

Esta implementación mantiene la diferencia entre contención y referencia. Una
contención crea estructura jerárquica en el espacio de trabajo, mientras que una
referencia selecciona un elemento que ya existe. La separación conserva la
información relacional del modelo de dominio.

Cuando existe una referencia opuesta, \texttt{synchronizeOppositeReferences}
calcula los valores inversos y actualiza el bloque destino. Una bandera
\texttt{\_\_syncingOpposite}\allowbreak\texttt{References} y la desactivación temporal de eventos
evitan que esa escritura genere un ciclo de notificaciones.

\subsection{Coordinación reactiva y protección de la exportación}

Además del listener específico instalado por \texttt{initValidations}, el
script de referencias registra el listener de coordinación del Listado
\ref{lst:listener-runtime-blockly}. \texttt{workspace} vuelve a ser el espacio
Blockly activo y \texttt{event} describe un único cambio: su propiedad
\texttt{type} indica la clase de evento, \texttt{blockId} identifica el bloque
y \texttt{name} identifica el campo cuando corresponde. Las comprobaciones
con \texttt{typeof} permiten reutilizar el mismo listener aunque un dominio no
genere validaciones o vista de salida.

\begin{lstlisting}[style=tfmjavascript, caption={Actualización reactiva del editor generado comentada línea a línea}, label={lst:listener-runtime-blockly}]
// Registra una funcion que recibe cada cambio del espacio de trabajo.
workspace.addChangeListener(function(event) {
    // Filtra los movimientos de bloques.
    if (event.type === Blockly.Events.BLOCK_MOVE ||
        // Incluye la creacion de un bloque.
        event.type === Blockly.Events.BLOCK_CREATE ||
        // Incluye la eliminacion de un bloque.
        event.type === Blockly.Events.BLOCK_DELETE ||
        // Incluye los cambios de campos y propiedades.
        event.type === Blockly.Events.BLOCK_CHANGE) {
        // Reconstruye las opciones de referencias disponibles.
        updateReferenceDropdowns(workspace);
        // Mantiene los dos extremos de las referencias opuestas.
        synchronizeOppositeReferences(workspace, event);
        // Comprueba que el entorno de validacion este cargado.
        if (typeof applyValidationWarnings === 'function')
            // Recalcula y muestra los avisos de validacion.
            applyValidationWarnings(workspace);
        // Comprueba que exista la vista de salida.
        if (typeof updateOutput === 'function') updateOutput();
    // Finaliza la reaccion ante eventos estructurales.
    }
// Finaliza y registra la funcion listener.
});
\end{lstlisting}

Antes de exportar JSON, XMI o código, \texttt{confirmExportIfInvalid} vuelve a
ejecutar las validaciones y solicita confirmación si quedan advertencias. El
usuario puede por tanto inspeccionar un modelo incompleto sin bloquear la
edición, pero la exportación no oculta sus problemas. Los límites numéricos
\texttt{min} y \texttt{max} se incorporan directamente a los campos Blockly.

\subsection{Inspección, edición visual y límites del entorno}

La página incluye además un ejecutor genérico de inspección.

El método \texttt{generateRuntimeScript} genera su código a partir del modelo.
Durante la ejecución, este código convierte el espacio de trabajo a la
representación JSON del dominio, recorre recursivamente sus nodos y resalta el bloque visitado
con controles de ejecución, pausa y paso. No ejecuta la semántica particular de
cada dominio; sirve para observar la estructura construida y comprobar el orden
de recorrido del modelo.

El ciclo de validación se completa con una utilidad de parche. Desde línea de
comandos puede ejecutarse sobre un fichero
\texttt{validation\_blocks.edited.json} y desde Eclipse está expuesta como
\texttt{Apply Validation Blocks to Source}. El parche se aplica de forma
conservadora: solo actualiza reglas que se pueden mapear de manera inequívoca a
la sintaxis textual o a anotaciones Ecore, y deja fuera expresiones que no tengan
una traducción directa.

El comportamiento generado sigue siendo deliberadamente ligero. No constituye
un motor OCL completo ni un verificador semántico general. Cubre cardinalidad,
obligatoriedad, unicidad, referencias opuestas, expresiones declaradas y el
subconjunto de invariantes OCL que los adaptadores pueden traducir a los
accesores disponibles en JavaScript.

\section{Integración con Eclipse y distribución}
\label{sec:implementacion-eclipse-distribucion}

\subsection{Registro de comandos y ejecución del manejador}

La integración con Eclipse se declara en el fichero \texttt{plugin.xml} del
bundle de interfaz. Este fichero registra los comandos
\texttt{generateBlocklyEditor} y \texttt{applyValidationPatch}, los asocia con
\texttt{GenerateBlocklyEditorHandler} y
\texttt{ApplyValidationPatchHandler}, y limita su visibilidad a selecciones de
un único fichero compatible. Las contribuciones al menú contextual incluyen
\texttt{.ecore} y \texttt{.m2b}; la extensión histórica
\texttt{.model2blockly} se conserva para poder abrir proyectos anteriores.

\texttt{GenerateBlocklyEditorHandler} extiende \texttt{AbstractHandler}. Su
método \texttt{execute} obtiene el \texttt{IFile} seleccionado, comprueba la
extensión y delega el trabajo en un \texttt{IRunnableWithProgress} ejecutado
por el servicio de progreso de Eclipse. Esta delegación evita bloquear la
interfaz mientras se cargan los recursos EMF, se genera el XMI intermedio y se
crean los artefactos web.

El Listado \ref{lst:eclipse-generate-runnable} muestra el núcleo del runnable.
\texttt{inputFile} es el fichero seleccionado; \texttt{monitor} representa el
progreso mostrado por Eclipse; y \texttt{files} es un mapa que relaciona cada
ruta relativa de salida con su contenido textual. La expresión condicional
elige una de las dos cargas, pero ambas ramas devuelven el mismo tipo de mapa y
convergen en \texttt{writeFiles}. Si ocurre un fallo, \texttt{e} contiene la
excepción original y se envuelve en \texttt{InvocationTargetException} para que
el servicio de progreso pueda devolverla al manejador.

\begin{lstlisting}[style=tfmjava, caption={Selección de la ruta de generación en Eclipse comentada línea a línea}, label={lst:eclipse-generate-runnable}]
// Indica que este metodo implementa la operacion exigida por el runnable.
@Override
// Recibe monitor, el objeto con el que Eclipse muestra el progreso.
public void run(IProgressMonitor monitor)
        // Declara el envoltorio usado para devolver errores al servicio Eclipse.
        throws InvocationTargetException {
    // Inicia un bloque que garantiza el cierre de la tarea de progreso.
    try {
        // Comunica a Eclipse el texto de la operacion que comienza.
        monitor.beginTask("Generating Blockly editor",
            // Usa progreso indeterminado porque cada modelo tiene otro tamano.
            IProgressMonitor.UNKNOWN);
        // Crea files, el mapa ruta-contenido que se escribira en el proyecto.
        Map<String, String> files =
            // Comprueba si inputFile pertenece a la ruta Ecore.
            "ecore".equals(inputFile.getFileExtension())
                // Carga, adapta, valida y genera desde el EPackage.
                ? generateFromEcore(inputFile)
                // Ejecuta la misma cadena desde el modelo analizado por Xtext.
                : generateFromModel2Blockly(inputFile);
        // Materializa todos los elementos de files en la carpeta de salida.
        writeFiles(inputFile, files, monitor);
    // Captura cualquier fallo de carga, transformacion o escritura.
    } catch (Exception e) {
        // Entrega el fallo al servicio de progreso sin perder su causa.
        throw new InvocationTargetException(e);
    // Ejecuta este bloque tanto si la generacion termina como si falla.
    } finally {
        // Marca la tarea como finalizada en la interfaz de Eclipse.
        monitor.done();
    // Finaliza el cierre garantizado de la tarea.
    }
// Finaliza la operacion del runnable.
}
\end{lstlisting}

Las dos ramas reutilizan la carga de la Sección
\ref{sec:carga-validacion-entradas}, los adaptadores de las Secciones
\ref{sec:implementacion-ecore-adapter} y
\ref{sec:implementacion-domainmodel-adapter}, y el generador de la Sección
\ref{sec:implementacion-generador-html}. En ambos casos se valida
\texttt{EditorSpec} antes de serializarlo, se vuelve a cargar su XMI y se
realiza una segunda validación antes de generar HTML y JavaScript.

\subsection{Escritura de artefactos en el espacio de trabajo}

El resultado común es el mapa de artefactos que recibe \texttt{writeFiles}.
Este método calcula la carpeta \texttt{*\_generated}, crea recursivamente sus
subdirectorios y elimina salidas obsoletas conocidas. Para cada entrada del
mapa obtiene un \texttt{IFile}, convierte el contenido a UTF-8 y usa
\texttt{IFile.create} cuando el recurso no existe o
\texttt{IFile.setContents} cuando debe actualizarlo. Al terminar, el proyecto
se refresca, se muestra la carpeta en \emph{Project Explorer} y se abre
\texttt{generation\_report.html} en el workbench.

\subsection{Diagnósticos y retorno de validaciones}

La integración también traduce los fallos de la transformación al mecanismo de
diagnósticos del IDE. Si falla la validación de \texttt{EditorSpec}, el
\texttt{BlocklySpecSourceMapper} permite crear un \texttt{IMarker.PROBLEM} sobre
el elemento de origen, incluyendo línea, ubicación, mensaje y sugerencia cuando
están disponibles. Los errores producidos por Xtext se convierten del mismo modo
en marcadores asociados al fichero \texttt{.m2b}. Por tanto, el usuario no recibe
solamente una excepción Java: el editor de origen se abre y Eclipse muestra la
ubicación del problema.

\texttt{ApplyValidationPatchHandler} implementa el camino inverso para las
reglas editadas visualmente. El manejador propone los ficheros
\texttt{validation\_blocks.json} de la salida correspondiente, ejecuta primero
\texttt{ValidationPatchService.dryRun} y presenta los cambios antes de pedir
confirmación. Solo después ejecuta \texttt{apply}, refresca el recurso y vuelve
a abrir la fuente. Cuando la escritura se realiza sobre el mismo fichero, el
servicio conserva previamente una copia con extensión \texttt{.bak}. Así, el
camino de retorno no modifica la fuente hasta que el usuario ha visto el
resumen del \emph{dry-run} y ha confirmado los cambios propuestos.

\section{Entradas independientes}
\label{sec:implementacion-standalone}

\subsection{Interfaces disponibles y convergencia de las dos entradas}

El bundle principal expone tres entradas Java ejecutables sin el workbench,
resumidas en el Listado \ref{lst:entradas-standalone}.

\begin{lstlisting}[style=tfmcli, caption={Interfaces comentadas de los puntos de entrada independientes}, label={lst:entradas-standalone}]
// Genera desde un EPackage cargado de un fichero Ecore.
EcoreToBlocklyMain <file.ecore> [output-dir]
// Genera desde un DomainModel analizado por Xtext.
Model2BlocklyToBlocklyMain <file.m2b> [output-dir]
// Aplica o simula cambios de validacion sobre una fuente.
ValidationPatchMain --source <file> --validation <json> [options]
\end{lstlisting}

\texttt{EcoreToBlocklyMain} es el punto de entrada de la ruta Ecore. Registra la
factoría de recursos, carga el \texttt{EPackage} y ejecuta
\texttt{EcoreAdapter}. Después valida y recarga el XMI intermedio antes de pasar
el resultado a \texttt{BlocklyCodeGenerator}.

\texttt{Model2BlocklyToBlocklyMain} implementa la ruta textual. Crea el injector
con la configuración independiente generada por Xtext, obtiene un \texttt{XtextResource},
ejecuta la validación sintáctica y semántica y llama a
\texttt{DomainModelAdapter}. A partir de \texttt{EditorSpec}, ambas clases
reutilizan exactamente la misma generación final. La extensión histórica
\texttt{.model2blockly} sigue la misma rama que \texttt{.m2b}; no existe un
tercer adaptador.

\subsection{Resolución de la salida y escritura en disco}

Si se omite el segundo argumento, las dos entradas calculan junto a la fuente
el directorio \texttt{<name>\_generated}. El Listado
\ref{lst:standalone-default-output} muestra este cálculo, compartido por las
dos clases. \texttt{inputPath} es la ruta recibida; \texttt{input} es su
representación como \texttt{File}; \texttt{name} conserva primero el nombre
completo; \texttt{dot} guarda la posición del último punto; y \texttt{parent}
es el directorio contenedor. Si la ruta no tiene padre, se utiliza el
directorio de trabajo representado por \texttt{"."}.

\begin{lstlisting}[style=tfmjava, caption={Cálculo del directorio de salida predeterminado comentado línea a línea}, label={lst:standalone-default-output}]
// Recibe inputPath, la ruta de la fuente indicada por el usuario.
private static String defaultOutputDir(String inputPath) {
    // Convierte la ruta textual en el objeto input de la API de ficheros.
    File input = new File(inputPath);
    // Obtiene name, inicialmente el nombre de fichero con su extension.
    String name = input.getName();
    // Localiza dot, la posicion del ultimo punto del nombre.
    int dot = name.lastIndexOf('.');
    // Comprueba que exista una extension despues del nombre base.
    if (dot > 0)
        // Elimina la extension y conserva solamente el nombre base.
        name = name.substring(0, dot);
    // Obtiene parent, el directorio que contiene el fichero de entrada.
    File parent = input.getParentFile();
    // Construye junto a parent una carpeta terminada en _generated.
    return new File(parent != null ? parent : new File("."),
        // Anade el sufijo al nombre base calculado anteriormente.
        name + "_generated").getPath();
// Finaliza el calculo de la ruta predeterminada.
}
\end{lstlisting}

Los artefactos Blockly se escriben bajo \texttt{html/}; el XMI intermedio, el
README y el informe se añaden en las mismas rutas que usa el complemento. Cada
entrada del mapa se convierte en un \texttt{File}; se crean sus directorios
padre y un \texttt{FileWriter} escribe el contenido. La consola muestra una
línea por fichero producido y, al finalizar, las rutas absolutas del informe,
el editor, el modelo intermedio y el espacio de validación. La Tabla

\subsection{Retorno de validaciones desde línea de comandos}

\texttt{ValidationPatchMain} reutiliza \texttt{ValidationSourcePatcher} para
aplicar el flujo de retorno de validaciones. El modo predeterminado es
\texttt{--dry-run}; \texttt{--apply} escribe los cambios y \texttt{--out}
permite conservar intacta la fuente original. Esta tercera entrada se utiliza
también para comprobar automáticamente que un modelo parcheado puede volver a
generar el editor. La clase interna \texttt{Options} conserva
\texttt{source}, la fuente que se modificará; \texttt{validation}, el JSON
editado; \texttt{output}, una salida alternativa; y el booleano
\texttt{apply}. Después de analizar los argumentos, este último selecciona
\texttt{ValidationSourcePatcher.apply} o
\texttt{ValidationSourcePatcher.dryRun}; el \texttt{PatchReport} resultante se
imprime en la consola con cambios, advertencias y notas.

\subsection{Separación respecto a la evaluación}

Estas pruebas responden a si la implementación conserva sus contratos: que una
entrada válida se transforme sin perder información, que los artefactos puedan
abrirse y que las funciones generadas reaccionen como se espera. No demuestran
por sí mismas que Model2Blockly reduzca el esfuerzo necesario para reconstruir
editores existentes ni que el resultado sea equivalente a una referencia
oficial. Esas preguntas requieren casos externos, métricas y criterios de
aceptación; por ello se reservan para el Capítulo~\ref{chap:evaluacion}.

\section{Resumen de implementación}
\label{sec:resumen-implementacion}

La implementación de Model2Blockly permite definir un dominio mediante Ecore
anotado o mediante la ruta textual \texttt{.m2b}. Ambas entradas se transforman
en el mismo \texttt{EditorSpec}, se validan antes y después de su serialización
XMI y reutilizan el generador HTML/JavaScript. A partir de ese contrato se
producen bloques, paleta, validaciones, referencias dinámicas, exportadores,
informes, un espacio de trabajo visual de validaciones y plantillas de código.

La misma cadena se expone mediante comandos de Eclipse y entradas Java
independientes. La feature y el repositorio p2 distribuyen el complemento; las
pruebas JUnit, de empaquetado y de humo en navegador cubren niveles
complementarios. Así, la implementación materializa alrededor del modelo
intermedio la arquitectura generativa definida en el capítulo anterior.
