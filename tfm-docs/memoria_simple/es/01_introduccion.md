# Introducción

La programación permite crear sistemas, automatizar tareas y expresar ideas de un dominio. Sin embargo, para muchos usuarios iniciales también supone una barrera importante. La literatura sobre programación basada en bloques muestra que estos entornos se usan a menudo para introducir a usuarios noveles en la programación, porque ofrecen una entrada más accesible que los lenguajes textuales tradicionales [@lin2021landscape]. Esta dificultad no aparece solo en la enseñanza de la informática. También afecta a usuarios no especialistas que podrían usar la programación para crear simulaciones, automatizar procesos o representar conocimiento de un dominio.

Los lenguajes basados en bloques aparecen como una respuesta a parte de estas barreras. En lugar de exigir que el usuario escriba instrucciones textuales desde cero, estos entornos presentan primitivas de programación como piezas visuales que pueden arrastrarse y conectarse. La forma de las piezas, sus colores, las etiquetas en lenguaje natural y la organización por categorías actúan como ayudas visuales para reconocer qué construcciones son posibles [@weintrop2018modalities]. Plataformas como Scratch, App Inventor, Tynker o MakeCode ilustran esta idea: ofrecen entornos en los que niños, estudiantes o usuarios con un perfil no técnico pueden construir programas mediante una sintaxis visual. Los estudios recientes sobre el ecosistema de programación por bloques muestran además una expansión hacia contextos diversos, incluyendo robótica, ciencia de datos, textiles electrónicos, desarrollo móvil y otros dominios de aplicación [@lin2021landscape]. Por ello, este tipo de interacción se ha extendido en contextos educativos y en herramientas orientadas a dominios concretos.

Blockly es una de las bibliotecas más utilizadas para construir este tipo de editores. Su documentación lo define como una biblioteca web que permite añadir a una aplicación un editor de código basado en bloques; el desarrollador define las conexiones, campos y generación asociada a cada bloque, mientras que la biblioteca se ocupa de la representación visual, el arrastre y el encaje de las piezas [@blocklyWhatIs]. La propia documentación de Blockly muestra que estos editores se aplican a dominios variados, como videojuegos, robótica, dibujo, análisis de datos o código específico de una aplicación [@blocklyDocs]. La literatura sobre programación por bloques indica además que el diseño de la modalidad de interacción condiciona las prácticas de programación que desarrollan los usuarios noveles [@weintrop2018modalities].

Sin embargo, el uso de Blockly no elimina por completo el coste de construir un lenguaje visual. La biblioteca proporciona la infraestructura de interacción, pero cada dominio requiere definir tipos de bloques, campos, entradas, categorías de la paleta, reglas de conexión, serialización, validaciones y, si procede, generadores de código. En otras palabras, crear un entorno basado en bloques con Blockly sigue exigiendo programación JavaScript de bajo nivel y un conocimiento detallado de la API de la biblioteca. Además, los entornos de programación por bloques no siguen un único diseño común. Lin y Weintrop señalan que cada entorno toma decisiones propias sobre cómo se organizan los bloques, si existe una relación con código textual y si se facilita una transición desde la programación visual hacia la programación textual [@lin2021landscape]. Por lo tanto, aunque Blockly reduce el esfuerzo frente a construir un editor visual desde cero, todavía queda un trabajo repetitivo y especializado cuando se desea crear un editor para cada nuevo dominio.

Esta situación plantea un problema de ingeniería de lenguajes. Si los conceptos principales de un dominio ya están descritos en un modelo o metamodelo, no debería ser necesario escribir la misma información otra vez como código JavaScript de Blockly. La ingeniería dirigida por modelos propone trabajar con modelos como artefactos principales para especificar, diseñar, probar y generar software [@jimenez2017scalable]. También se han señalado motivaciones como la reutilización, la reducción del tiempo de desarrollo y la mejora de calidad [@akdur2018survey]. Desde esta perspectiva, un editor Blockly puede verse como una sintaxis visual generada a partir de una descripción abstracta del dominio.

El ecosistema Eclipse ofrece tecnologías especialmente adecuadas para explorar esta idea. EMF proporciona una infraestructura para definir modelos estructurados y generar código a partir de ellos; su metamodelo Ecore permite representar clases, atributos, referencias, herencia, persistencia y soporte reflexivo [@emfOverview]. Xtext, por su parte, permite definir lenguajes textuales específicos de dominio y genera una infraestructura completa de parsing, enlace, validación, compilación y edición [@xtextProject]. La literatura sobre herramientas basadas en Xtext subraya además que, a partir de una gramática, Xtext genera un parser, un árbol de sintaxis abstracta basado en EMF y funcionalidades de editor integradas en Eclipse [@bettini2015xsemantics]. Estas tecnologías permiten definir dominios con precisión, pero no proporcionan automáticamente una representación visual basada en bloques.

El objetivo de este Trabajo Fin de Máster es desarrollar un entorno para crear lenguajes de dominio específico con sintaxis basada en bloques. La idea no es construir un único editor de bloques, sino una infraestructura que permita describir un dominio y generar de forma automática el código necesario para editarlo con Blockly.

La herramienta desarrollada se llama BlocklyDSL. Tiene dos rutas de entrada. La primera parte de metamodelos Ecore, que pueden enriquecerse con anotaciones sobre la sintaxis visual. En esta ruta, las clases se convierten en tipos de bloque, los atributos en campos, las referencias de contención en conexiones estructurales y las cardinalidades en reglas de comprobación. La segunda ruta parte de descripciones textuales definidas con Xtext. Esta sintaxis textual permite describir dominios de forma compacta y usar después la misma cadena de generación.

Ambas rutas se transforman en un modelo intermedio común, `BlocklyEditorSpec`. Este modelo contiene los elementos necesarios para generar el editor: tipos de bloque, categorías, campos, entradas de valor, referencias, validaciones y metadatos de interfaz. A partir de esta representación se genera un editor Blockly clásico en HTML/JavaScript y, además, una salida HTML que separa la configuración del dominio de una capa web reutilizable.

El desarrollo se ha organizado de forma incremental. Primero se abordó la generación básica de bloques y paletas desde modelos de dominio. Después se añadieron comprobaciones automáticas para detectar si faltan bloques requeridos por el modelo o si algún campo obligatorio queda vacío, junto con referencias entre elementos mediante listas desplegables dinámicas. Más tarde se incorporaron opciones de personalización visual, anotaciones de interfaz, validaciones semánticas simples y generación de código a partir de los bloques. La herramienta se valida mediante AppMaker, un ejemplo conductor definido tanto con el DSL textual como con Ecore anotado. Este ejemplo permite comparar las dos rutas de entrada sobre un mismo dominio y observar el editor Blockly generado en ambos casos.

Las principales aportaciones de este TFM son las siguientes. En primer lugar, se define una arquitectura que conecta Ecore, Xtext y Blockly mediante un modelo intermedio propio. En segundo lugar, se implementan adaptadores capaces de extraer de las entradas de dominio la información necesaria para construir un editor visual. En tercer lugar, se desarrolla un generador que produce bloques, paletas, páginas de edición, serialización y validaciones ejecutables en el navegador. En cuarto lugar, se extiende la propuesta con referencias, personalización visual, generación de código y una salida HTML. Por último, se evalúa la solución mediante pruebas automáticas y casos de uso representativos.

El alcance del trabajo se centra en la generación de editores visuales y en la demostración de que el enfoque puede aplicarse a dominios distintos. Quedan fuera del objetivo principal la importación genérica de modelos XMI ya existentes a un espacio Blockly, la integración de lenguajes de restricciones complejos como OCL y la construcción de interfaces finales altamente especializadas para cada dominio. Estos puntos marcan el límite del trabajo actual y se plantean como posibles extensiones futuras. La contribución central es reducir el esfuerzo necesario para crear editores Blockly específicos mediante metamodelos, DSLs y generación de código.
