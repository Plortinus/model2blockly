# 第 1 章：引言（中文审阅稿）

## 本章定位

本章已经按原始 TFM oferta 来组织，核心题目是：

**“Un entorno para la creación de lenguajes de dominio específico con sintaxis basada en bloques”**

因此论文主线不是单纯介绍 Blockly，也不是单纯介绍 MDE，而是：

1. 块式语言适合儿童、学生和非技术用户，典型平台包括 Scratch、App Inventor、Tynker、MakeCode。
2. Blockly 可以创建块式环境，但仍需要较底层的 JavaScript 编程。
3. 本 TFM 用建模语言工程/MDE 技术解决这个重复开发问题。
4. 从元模型出发，必要时通过注解补充块式语法信息，自动生成使用 Blockly 的编辑器代码。
5. 最终目标是一个创建带块式语法的领域专用语言环境，而不是一个单独 demo。

编程是一种表达性和构造性的活动，但对许多初学者来说，它也有明显的进入门槛。ScienceDirect 上 Lin 与 Weintrop 的综述性论文指出，基于积木的编程环境已经成为初学者接触编程的重要方式，因为它们相对传统文本语言提供了更低的进入门槛。因此，问题不只是“学生学编程难”，也包括非技术用户难以把编程作为创建模拟、自动化任务或表达领域知识的工具。

基于积木的语言可以部分缓解这些门槛。它不是让用户从零开始输入文本代码，而是把程序构造表示成可以拖拽和连接的可视化部件。Scratch、App Inventor、Tynker 和 MakeCode 这类平台体现了这种思路：儿童、学生或非技术用户可以用可视化语法构建程序。Weintrop 与 Wilensky 在 ScienceDirect 发表的研究说明，编程界面的 modality 会影响新手形成的编程实践；Lin 与 Weintrop 的综述也说明，块式编程生态已经扩展到机器人、数据科学、电子纺织品、移动开发等多种场景。因此，块式交互在教育和领域工具中都有实际基础。

Blockly 是构建这类编辑器的重要 Web 库。Blockly 官方文档说明，它允许开发者在应用中加入基于积木的代码编辑器：开发者定义积木连接、字段和生成逻辑，Blockly 负责渲染、拖拽和拼接等底层交互。Blockly 文档还列出它可以服务于游戏、机器人、绘图、数据分析和应用专用代码等多种场景。关于“界面设计会影响用户实践”和“块式环境存在多种设计差异”的判断，则用 ScienceDirect 上 Weintrop/Wilensky 以及 Lin/Weintrop 的论文支撑。

但是，使用 Blockly 并不等于完全消除了构建可视化语言的成本。Blockly 提供的是交互基础设施；每一个新领域仍然需要定义积木类型、字段、输入、工具箱分类、连接规则、序列化、校验，以及必要时的代码生成器。也就是说，Blockly 降低了从零实现可视化编辑器的成本，但仍然要求开发者写较底层的 JavaScript/Blockly 代码；如果每个领域都手写一套，就会产生重复且专业化的工作。

这就引出一个软件工程和语言工程问题：如果一个领域的核心概念已经能用模型或元模型描述，为什么还要再手动把这些概念编码成 JavaScript 积木？模型驱动工程正是希望通过模型提高抽象层次，用领域概念来表达系统，从而降低对平台细节的依赖。这里主要使用 ScienceDirect 上 Jiménez-Pastor、Garmendia 与 de Lara 关于 MDE 的论文作为理论支撑；Akdur、Garousi 与 Demirörs 的工业调查论文则支撑 MDE 在实践中常见的动机，例如节省成本、缩短开发时间、提高复用和质量。

Eclipse 生态中的 EMF/Ecore 和 Xtext 适合探索这个问题。EMF 官方文档说明，EMF 可以定义结构化模型并生成代码，Ecore 可以表示类、属性、引用、继承、持久化和反射操作。Xtext 官方文档说明，Xtext 可以定义领域专用文本语言，并生成 parser、linker、validator、compiler/editor 等基础设施。ScienceDirect 上 Bettini 关于 Xsemantics 的论文也说明，Xtext 从语法定义生成 parser、基于 EMF 的抽象语法树和 Eclipse 编辑器功能。不过，这些技术虽然能精确定义领域，却不会自动给出基于 Blockly 的可视化语法。

本 TFM 位于这两个方向的交叉点：目标是实现一个“创建带块式语法的领域专用语言”的环境。核心思想不是为某一个例子做一个 Blockly demo，而是让 Ecore 元模型，必要时加上描述块式语法的注解，或者由 Xtext DSL 描述的领域模型，先转换成一个编辑器中间模型，再从这个中间模型生成可运行的 HTML/JavaScript 编辑器。这样，领域知识保留在抽象、可复用的模型层，而可视化语法通过代码生成系统化地产生。

本项目实现的工具称为 BlocklyDSL。它支持两条输入路径：一条是 Ecore 元模型路径，另一条是用 Xtext 定义的文本 DSL 路径。Ecore 路径直接对应 oferta 中“从元模型生成 Blockly 代码”的要求：类映射为积木类型，属性映射为字段，包含引用映射为结构连接，基数映射为校验规则。DSL 路径则提供一种更紧凑的文本方式来定义领域语言，并复用同一套生成架构。无论输入来自哪条路径，系统都会把信息规范化到统一的中间模型。这个中间模型包含生成编辑器所需的核心信息：积木类型、分类、字段、值输入、引用、校验规则和界面元数据。基于它，系统生成 HTML/JavaScript 版 Blockly 编辑器。

项目是增量完成的。首先实现了从领域模型生成基础积木和工具箱；之后加入从基数和必填字段推导出的校验，以及用动态下拉菜单实现的元素引用；随后加入视觉个性化、界面注解和积木到代码的生成。工具通过 AppMaker 进行验证，并分别用文本 DSL 和带注解的 Ecore 描述同一个低代码应用构建领域。这样可以直接比较两条输入路线是否复用同一个中间模型和生成器。

本 TFM 的主要贡献有五点：第一，定义了一个连接 Ecore、Xtext 和 Blockly 的生成架构；第二，实现了从不同输入提取编辑器信息的适配器；第三，实现了生成积木、工具箱、编辑页面、序列化和校验的代码生成器；第四，扩展了引用、可视化个性化和代码生成；第五，用自动化测试和代表性案例评估了工具。

项目范围集中在“生成可视化编辑器”和“证明方法适用于不同领域”。不作为核心目标的内容包括：把已有 XMI 模型通用导入 Blockly、集成 OCL 这类复杂约束语言、以及为每个领域做高度专用的最终业务 UI。这些作为未来工作，不影响本文核心贡献：用元模型、DSL 和代码生成降低构建领域专用 Blockly 编辑器的成本。

论文后续结构如下：先介绍目标和需求；再说明技术和相关概念；然后描述 BlocklyDSL 的架构、中间模型和输入适配器；之后说明生成器、校验、引用、个性化和代码生成的实现；接着展示案例和评估；最后给出结论和未来工作。
