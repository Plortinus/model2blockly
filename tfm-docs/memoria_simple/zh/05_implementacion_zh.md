# 第 5 章中文审阅稿：BlocklyDSL 的实现

这一章进入具体实现。第 4 章解释“为什么这样设计”，第 5 章解释系统怎样把这个设计落地：从领域描述读取信息，转换成统一的编辑器规格，再生成可运行的 Blockly 编辑器。

写作时要注意：正式论文不适合写成代码文件说明书。因此这一章重点说明实现思路、转换规则和工程证据，只在必要时保留少量关键技术名。

## 5.1 项目组织

项目按 Xtext/EMF 的常见结构组织，分成语言核心、IDE 支持和 Eclipse UI 集成几部分。核心部分负责语法、适配、中间模型、生成器、独立执行入口和测试；IDE 与 UI 部分主要来自 Xtext 工程，用于在 Eclipse 中提供编辑支持。

这种组织方式和第 4 章架构一致：

| 实现部分 | 作用 |
|---|---|
| 文本语言定义 | 描述领域、块、字段、引用、验证和界面选项 |
| 中间模型 | 统一表示生成 Blockly 编辑器所需的信息 |
| 输入适配层 | 把 Ecore 或文本 DSL 转换成中间模型 |
| 生成层 | 生成 HTML/JavaScript 或 HTML 形式的 Blockly 编辑器 |
| 验证层 | 在生成前和运行时发现不一致或不完整的模型 |
| 测试层 | 对转换和生成结果进行可重复检查 |

本节的核心论点是：项目结构不是随意划分，而是对应“输入、抽象表示、生成、执行、验证”这条模型驱动流程。

## 5.2 文本 DSL 的实现

文本 DSL 由 Xtext 定义。它允许用户用紧凑语法声明一个领域，包括领域名称、分类、类、属性、包含关系、非包含引用、表达式输入、约束、工作区选项、界面选项和代码模板。

和直接写 Blockly JavaScript 相比，这种 DSL 更接近领域建模语言：用户描述“领域里有什么概念、概念之间如何连接、哪些信息必须填写”，而不是手写每个积木在 Blockly 里的 JSON 结构。

生成前会进行静态检查，例如：

- 是否出现重复名称；
- cardinality 是否合理；
- 是否所有可实例化概念都缺失；
- 输出型块是否错误地包含子语句；
- 表达式输入是否连接到合适的输出型概念；
- 布尔字段是否被错误声明为必填；
- 顺序约束是否用在不适合的块类型上；
- 界面 widget 和字段类型是否匹配。

这里的论点是：错误越早发现越好。文本层的检查可以在生成网页之前提示建模者，避免把明显错误传播到运行时编辑器。

## 5.3 中间模型

中间模型是本项目的关键实现边界。它保存生成 Blockly 编辑器需要的信息，例如领域名称、分类、块类型、字段、结构输入、值输入、引用、验证规则、工作区选项和代码导出元数据。

每个块类型记录：

- 可见标签、颜色和分类；
- 是否抽象、是否输出型、是否有父类型；
- 普通字段，例如文本、数字、布尔、枚举、颜色和角度；
- 结构性输入，用于表示 containment；
- 值输入，用于表示表达式或参数；
- 动态引用字段，用于表示 non-containment reference；
- 与 cardinality、必填项或顺序有关的验证规则。

本节的核心论点是：中间模型让输入和输出解耦。Ecore 路线和文本 DSL 路线都转换到同一个抽象表示；HTML 输出从这个表示生成。

## 5.4 Ecore 输入路线

Ecore 输入路线直接回应 TFM 的核心目标：从元模型生成 Blockly 编辑器。

基本映射关系如下：

| Ecore 建模元素 | Blockly 编辑器中的结果 |
|---|---|
| 类 | 一个块类型 |
| 属性 | 块上的字段 |
| 包含引用 | 可嵌套子块的结构输入 |
| 非包含引用 | 指向已有元素的动态下拉引用 |
| 继承 | 类型化连接规则 |
| cardinality | 运行时 warning 或输入限制 |
| 枚举 | 下拉字段 |

没有 Blockly 注解时，系统也会根据 Ecore 本身的结构生成基础编辑器。例如，属性会变成字段，包含引用会变成子块区域，非包含引用会变成动态引用，继承关系会影响可连接类型。

当 Ecore 本身不能表达 Blockly 需要的展示信息时，可以通过注解补充。例如：

- Blockly 展示信息：标签、颜色、分类、tooltip、inline、输出型块、数值范围、shadow block；
- UI 信息：inspector 中的 widget、分组、排序、帮助文本；
- 代码导出信息：代码模板和语言扩展名；
- 验证信息：简单 OCL-like 规则或自定义 JavaScript 条件。

这里要表达的不是“必须写很多注解”，而是“优先利用 Ecore 的结构，只有视觉语法、交互细节和导出规则不足时才补充注解”。

## 5.5 文本 DSL 输入路线

文本 DSL 路线和 Ecore 路线共享同一个中间模型，但输入方式更直接。因为 DSL 中已经显式区分属性、包含关系、引用和值输入，所以它适合快速构造案例、测试生成器能力，也适合在没有现成 Ecore 元模型时进行原型建模。

典型映射包括：

- 属性变成 Blockly 字段；
- containment 变成结构性子块输入；
- reference 变成动态下拉引用；
- value input 变成表达式连接口；
- `required` 变成必填 warning；
- `must follow` 变成顺序 warning。

连接形式也可以从模型结构推断：输出型概念生成表达式块，有父类型的概念参与类型化连接，有 containment 的顶层概念可作为根块，普通概念生成可堆叠块。

这一节的论点是：文本 DSL 是 Ecore 的补充，不是替代。它帮助快速验证生成链路，同时证明生成器并不依赖单一输入格式。

## 5.6 HTML/JavaScript 生成

经典输出生成一个可以直接在浏览器中运行的 Blockly 编辑器。生成内容包括：

- 块定义；
- 工具箱分类；
- JSON 和代码导出逻辑；
- 运行时验证逻辑；
- 可打开的 HTML 页面；
- 生成报告、示例模型和使用说明。

字段映射遵循 Blockly 原生能力：字符串变成文本输入，数字变成数字字段，布尔值变成复选框，枚举变成下拉框，颜色和角度使用对应 Blockly 字段。containment 生成结构性输入，value input 生成表达式连接，reference 生成动态下拉。

本节的核心论点是：生成器不是只生成外观，而是生成一个可编辑、可验证、可导出、可演示的完整编辑器。

## 5.7 运行时验证和引用

论文需要清楚区分两类验证：

1. 生成前验证：检查领域定义本身是否存在明显错误。
2. 运行时验证：用户在 Blockly workspace 中拖块时，检查当前模型是否完整或一致。

运行时验证主要包括：

- containment 数量是否满足最小值和最大值；
- 必填字段是否为空；
- 必填引用是否缺失；
- 某些块是否满足顺序约束；
- 简单 OCL-like 条件是否能够转成运行时 warning。

这些验证以 warning 为主，不是完整 OCL 引擎，也不是阻止用户编辑的强约束。这样做符合 Blockly 编辑器的交互特点：用户可以先构造不完整模型，再逐步修正；导出前系统再提示是否存在 warning。

动态引用的实现思路是：编辑器从 workspace 中收集已有块，根据目标类型和子类型关系筛选候选对象，再在下拉框中显示可引用对象。这样可以把 containment 和 reference 明确区分开：前者表示结构上的父子包含，后者表示指向已有元素。

## 5.8 HTML 输出

除了经典 HTML/JavaScript 输出，项目还支持生成 HTML 形式的编辑器。它把领域相关配置和可复用运行时界面分开，适合进一步集成 inspector、导出面板和更完整的用户界面。

这一输出不是 TFM 的最低要求，但它加强了架构论证：只要中间模型稳定，就可以增加新的生成目标，而不需要重写 Ecore 或文本 DSL 的输入路线。

## 5.9 Ecore 独立执行入口

为了让 Ecore 开发者更容易验证系统，项目提供了从 Ecore 直接生成编辑器的独立执行方式。用户不必先写文本 DSL，也不必手动复制生成文件；给定 Ecore 元模型后，系统可以生成 HTML 输出。

这一点对论文很重要，因为 TFM 原始方向强调“从 metamodel 生成 Blockly 代码”。独立 Ecore 路线证明当前系统并不是只能处理自定义文本 DSL。

## 5.10 测试

项目测试覆盖五个层面：

| 测试层面 | 作用 |
|---|---|
| 中间模型 | 检查默认值、结构组织和基本行为 |
| Ecore 转换 | 检查类、属性、引用、继承、枚举、cardinality 和注解映射 |
| 文本 DSL 转换 | 检查 DSL 结构是否正确进入中间模型 |
| HTML/JavaScript 生成 | 检查生成的块、工具箱、验证、导出和页面结构 |
| HTML 输出 | 检查生成编辑器的结构和核心文件 |

这一节的论点是：评估不是只靠手工打开几个例子，而是把转换和生成链路拆成可测试层次。这样更容易发现问题，也更适合在后续扩展 Ecore 语法、验证规则或生成目标时保持一致性。

## 维护同步说明

如果后续继续修改代码，论文和中文审阅稿应按下面顺序同步：

1. 先改真实代码和测试。
2. 运行或至少检查对应验证。
3. 再更新论文中受影响的章节。

通常对应关系是：

| 改动类型 | 论文需要更新的位置 |
|---|---|
| 改文本语法 | 第 5.2 节，可能也影响第 4 章架构 |
| 改 Ecore 转换 | 第 5.4 节 |
| 改文本 DSL 转换 | 第 5.5 节 |
| 改中间模型 | 第 4 章和第 5.3 节 |
| 改 HTML/JavaScript 生成 | 第 5.6 / 5.7 节 |
| 改 HTML 输出 | 第 5.8 节 |
| 加案例 | 第 6 章案例与评估 |
| 加测试 | 第 5.10 和第 6 章评估 |

这种对应关系可以避免论文描述和实现脱节。当前写法按架构层次组织，因此后续如果只改某一层，通常只需要更新相应小节和第 6 章的评估材料。
