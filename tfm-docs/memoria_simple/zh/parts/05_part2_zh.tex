\subsection{包含关系与引用的转换}

对 \texttt{EReference} 的处理取决于其功能。\texttt{input\_value} 注解生成
水平连接；带有 \texttt{containment=true} 的引用生成结构输入；其余引用则
生成动态选择器。代码清单 \ref{lst:conversion-containment-ecore} 仅保留
\texttt{Board.items} 所使用的分支，省略了不会改变这一结构创建过程的
其他分支。

在该代码片段中，\texttt{eRef} 是输入的 \texttt{EReference}，
\texttt{refAnn} 是其可选的 Blockly \texttt{EAnnotation}。\texttt{bt} 是所属
类的 \texttt{BlockTypeSpec}，\texttt{sis} 是输出的
\texttt{Statement}\allowbreak\texttt{InputSpec}。\texttt{check} 保存连接
所接受的类型；\texttt{hasContainments} 记录该块包含子元素。数据流为
\texttt{eRef} $\rightarrow$ \texttt{sis} $\rightarrow$ \texttt{bt}。

\begin{lstlisting}[style=tfmjavaecore, captionpos=t, caption={Ecore 包含关系转换的带注释代码片段}, label={lst:conversion-containment-ecore}]
// eRef 是当前引用；选择其包含关系分支。
if (eRef.isContainment()) {
    // hasContainments 记录 bt 包含子元素。
    hasContainments = true;
    // 创建 sis，即由 eRef 生成的结构输入。
    StatementInputSpec sis = new StatementInputSpec();
    // 将 eRef 的名称复制到 sis。
    sis.setName(eRef.getName());
    // refAnn 是可选注解；从中获取 check 类型。
    String check = refAnn != null
        // 读取 Blockly 注解中的 check 值。
        ? refAnn.getDetails().get("check") : null;
    // 在 sis 中配置显式类型，或使用 eRef 的 EClass。
    sis.setCheckType(check != null && !check.isBlank()
        // 保留注解中指定的类型。
        ? check
        // 根据被包含的 EClass 推断类型。
        : eRef.getEReferenceType().getName());
    // 将 eRef 允许的最小数量复制到 sis。
    sis.setLowerBound(eRef.getLowerBound());
    // 将 eRef 的最大值复制到 sis，并规范化开放上界。
    sis.setUpperBound(eRef.getUpperBound() == -1
        // 在通用模型中用零表示开放上界。
        ? 0 : eRef.getUpperBound());
    // 将 sis 加入块描述符 bt。
    bt.getStatementInputs().add(sis);
// 结束包含关系的转换。
}
\end{lstlisting}

因此，对于 \texttt{Board.items}，适配器会创建一个名为
\texttt{items} 的 \texttt{StatementInputSpec}，其接受类型为
\texttt{WorkItem}，下界为一，上界为四。由于存在继承关系，
\texttt{Task} 和 \texttt{Note} 块都能满足该类型。基数还用于生成
验证规则，因此当看板包含少于一个或多于四个元素时，编辑器会发出
警告。

\subsection{连接与继承的推断}

连接推断同样在适配器中完成。包含其他元素且本身不被其他元素包含的
类可以转换为没有垂直连接的根块。继承自超类的类可以生成类型化连接。
标记为输出块的类会生成值连接器。这种推断很重要，因为用户无需为每个
类手工编写 Blockly 连接规则。在第一个示例中，\texttt{Board} 被识别为
根块，而 \texttt{Task} 和 \texttt{Note} 会获得与 \texttt{WorkItem}
兼容的连接。

\section{来自文本路线 \texttt{.m2b} 的适配器}
\label{sec:implementacion-domainmodel-adapter}

文本路线的适配器同样由 Java 手工实现。
\texttt{DomainModelAdapter.fromDomainModel} 接收 Xtext 生成的 EMF 根对象，
并依次执行 \texttt{convertCategories}、\texttt{convertClasses}、
\texttt{convertValidations} 和 \texttt{convertConstraints}。随后，它生成
由基数、必填性和唯一性推断出的验证规则，最后通过
\texttt{convertWorkspace}\allowbreak\texttt{Options} 复制工作区选项。
所得 Java 对象随后返回到代码清单 \ref{lst:entrada-adaptadores-java} 中的
\texttt{toEditorSpec} 方法，并在那里转换为与 Ecore 路线相同的通用 EMF
模型。

该映射比 Ecore 更直接，因为语法已经区分了 Model2Blockly 所需的特定
概念。属性转换为字段，包含关系转换为结构输入，引用转换为动态下拉框，
值输入转换为水平连接。顺序约束转换为验证规则，标记为必填的字段则生成
必填性检查。

每个类的转换通过遍历 Xtext 生成的 \texttt{Feature} 列表来实现。
代码清单 \ref{lst:despacho-domainmodel-adapter} 展示了核心分派逻辑。
每个具体类型都会交给专用方法处理，输入名称则加入
\texttt{orderedInputNames}；这样，在构造块时可以保留 \texttt{.m2b}
文件中的书写顺序。

\begin{lstlisting}[style=tfmjava, captionpos=t, caption={\texttt{DomainModelAdapter} 中 DSL 元素分派的带注释代码}, label={lst:despacho-domainmodel-adapter}]
// 按顺序遍历 DSL 类的特征。
for (Feature feature : cls.getFeatures()) {
    // 识别可编辑属性。
    if (feature instanceof Attribute) {
        // 将属性转换为通用模型中的字段。
        FieldSpec field = convertAttribute((Attribute) feature);
        // 将字段加入块类型。
        bt.getFields().add(field);
        // 保留其在 .m2b 文件中声明的位置。
        bt.getOrderedInputNames().add(field.getName());
    // 识别包含关系的层次结构。
    } else if (feature instanceof Containment) {
        // 声明生成的结构输入。
        StatementInputSpec input =
            // 复制类型、基数和界面元数据。
            convertContainment((Containment) feature);
        // 将语句输入加入块。
        bt.getStatementInputs().add(input);
        // 保留它相对于其他输入的位置。
        bt.getOrderedInputNames().add(input.getName());
    // 识别对现有对象的引用。
    } else if (feature instanceof Reference) {
        // 声明生成的引用下拉框。
        ReferenceFieldSpec reference =
            // 复制目标、必填性和显示信息。
            convertReference((Reference) feature);
        // 将引用加入块类型。
        bt.getReferenceFields().add(reference);
        // 同样保留其可视位置。
        bt.getOrderedInputNames().add(reference.getName());
    // 识别水平值连接。
    } else if (feature instanceof ValueInput) {
        // 转换接受的类型和可能的阴影块。
        ValueInputSpec input = convertValueInput((ValueInput) feature);
        // 将值输入加入块。
        bt.getValueInputs().add(input);
        // 在统一顺序中记录其名称。
        bt.getOrderedInputNames().add(input.getName());
    // 结束应用于当前特征的分支。
    }
// 结束对该类的遍历。
}
\end{lstlisting}

实现还利用继承信息来确定连接形态。标记为输出块的类会转换为值块；
具有超类的类会生成类型化连接；具有包含关系且没有超类的类可以作为
根块；普通类则生成为可堆叠块。通过这种方式，文本语法中声明的语义会
转换为 Blockly 可视规则，领域作者无需了解该库的底层 API。

系统使用 Xtext 生成的 Java 类型（\texttt{ClassDef}、
\texttt{Attribute}、\texttt{Containment}、\texttt{Reference} 和
\texttt{ValueInput}）读取主要结构。只有部分界面、代码和工作区选项
通过反射获取：\texttt{eClass()} 使用 \texttt{getEStructuralFeature}
定位特征，\texttt{eGet} 则获取其值。这一决定使语法中新加入的元数据
可以在重新生成全部访问器之前被读取，同时仍能在确定块结构的遍历过程
中保留静态检查。

\section{HTML/JavaScript 生成器}
\label{sec:implementacion-generador-html}

HTML/JavaScript 输出生成器将中间模型转换为在浏览器中打开编辑器所需
的产物：块、工具箱、导出、验证、编辑页面、独立页面、验证工作区、
示例模型和生成报告。该输出使用 Blockly 定义块、注入工作区、管理
工具箱、序列化并生成代码 \cite{blocklyDocs}。

代码生成主要使用 Xtend 实现。主类
\texttt{Blockly\allowbreak{}Code\allowbreak{}Generator.xtend} 接收一个
\texttt{EditorSpec}，并生成从文件名到文本内容的有序映射。代码清单
\ref{lst:entrada-generador-xtend} 展示了入口方法：每个
\texttt{generate*} 函数返回一个字符串，该映射则保存该字符串与其目标
文件之间的关系。

\begin{lstlisting}[style=tfmxtend, captionpos=t, caption={带逐行注释的 \texttt{BlocklyCodeGenerator.xtend} 入口方法}, label={lst:entrada-generador-xtend}]
// 声明接收通用中间模型的操作。
def Map<String, String> generate(EditorSpec spec) {
    // 创建保留产物顺序的映射。
    val files = new LinkedHashMap<String, String>()
    // 获取基础名称；若未定义，则使用 domain。
    val base = spec.domainName ?: "domain"
    // 生成块的 JSON 定义。
    files.put(base + "_blocks.js", generateBlocksJs(spec))
    // 生成工具箱及其类别。
    files.put(base + "_toolbox.js", generateToolboxJs(spec))
    // 生成各个块的导出函数。
    files.put(base + "_generators.js", generateGeneratorsJs(spec))
    // 生成工作区验证规则。
    files.put(base + "_validations.js", generateValidationsJs(spec))
    // 生成模块化编辑器页面。
    files.put(base + "_editor.html", generateEditorHtml(spec))
    // 生成独立演示页面。
    files.put(base + "_standalone.html", generateStandaloneHtml(spec))
    // 注册用于可视化编辑规则的页面。
    files.put("validation_workspace.html",
        // 将其内容委托给专用生成器。
        ValidationWorkspaceHtmlGenerator.generate(spec))
    // 注册规则的序列化表示。
    files.put("validation_blocks.json",
        // 将验证规则转换为块树。
        ValidationBlockModelGenerator.generate(spec))
    // 注册这些树的 JavaScript 求值器。
    files.put("validation_runtime.js",
        // 生成与浏览器兼容的经典 JavaScript。
        ValidationRuntimeGenerator.generateClassicJs(spec))
    // 生成用于测试编辑器的初始模型。
    files.put("sample_model.json", SampleModelGenerator.generate(spec))
    // 返回路径和内容，此时尚未写入磁盘。
    return files
// 结束生成器的主操作。
}
\end{lstlisting}

选择 Xtend 作为生成机制，是因为它与 Xtext 集成良好，并可在 Eclipse
项目中编写易读的文本模板。本项目没有使用 Acceleo 或外部模板引擎。
示例模型、验证运行环境和规则可视化视图等辅助部分由单独的 Java 类
实现，以保持各自职责边界清晰。

该映射不会直接写入磁盘。\texttt{GenerateBlocklyEditorHandler} 在其
路径前添加 \texttt{html/}，并加入三个在 Xtend 之外生成的结果：中间
XMI、\texttt{README.md} 和生成报告。最后，\texttt{writeFiles} 创建
工作区中的 \texttt{IFile} 并刷新项目。这种分离使同一生成器可由
独立入口复用，而无需依赖 Eclipse API。

报告由 \texttt{GenerationReport}\allowbreak\texttt{HtmlRenderer}
构建。该类接收源文件、\texttt{EditorSpec} 和产物清单，并生成
\texttt{generation\_}\allowbreak\texttt{report.html}。
\texttt{README.md} 则在处理器或相应独立入口中组装，因为它包含针对
执行方式定制的说明。这两个结果都会在写入之前加入映射，但不属于
\texttt{BlocklyCodeGenerator} 的直接输出。

块生成从 \texttt{generateBlocks}\allowbreak\texttt{Array} 开始；该方法
筛选具体类型并调用
\texttt{blockTypeTo}\allowbreak\texttt{BlockJson}。后者创建字段、引用和输入的映射，并遍历
\texttt{orderedInput}\allowbreak\texttt{Names}，以保留适配器确定的顺序。每个元素分别交由
\texttt{fieldToArg}、\texttt{referenceToArg}、
\texttt{valueInputToArg} 或
\texttt{statementInput}\allowbreak\texttt{ToArg} 处理。最后，对
\texttt{Connection}\allowbreak\texttt{Type} 执行的
\texttt{switch} 会生成自由类型或类型化的
\texttt{previous}\allowbreak\texttt{Statement}、
\texttt{nextStatement} 或 \texttt{output}。抽象类保留在模型中，以便
解析继承和连接，但不会作为可实例化块加入输出。

工具箱生成过程会产出用户可用的块集合。若没有类别，生成器可以输出
简单工具箱；若存在类别，则生成带类别的工具箱，并在已定义子类别时将
其一并纳入。还会加入 Blockly 的内置类别，如逻辑、循环、数学、变量
和函数，使各领域可在必要时将领域块与通用构造结合使用。

\texttt{ContentForm} 的垂直布局也不是手写在 HTML 中的。当块请求
\texttt{inputsInline=false} 且没有声明自定义 \texttt{message0} 时，
\texttt{blockTypeTo}\allowbreak\texttt{BlockJson} 会推导出这一布局。在代码清单
\ref{lst:filas-campos-blockly} 中，\texttt{bt} 是当前正在生成的
\texttt{BlockTypeSpec}，\texttt{rowMessages} 为每个字段保存一个标签，
\texttt{rowArgs} 则保存相应控件的 JSON 片段。\texttt{messageIndex}
从一开始，因为 \texttt{message0} 保留给块的标题。

\begin{lstlisting}[float=htbp, style=tfmxtend, captionpos=t, caption={当 \texttt{inputsInline=false} 时逐字段生成行的带注释代码}, label={lst:filas-campos-blockly}]
// 判断 bt 是否应将每个输入显示在独立行中。
val useStackedRows = bt.message0 === null
    && Boolean.FALSE.equals(bt.inputsInline) && !rowArgs.empty
// 仅在满足该条件时生成垂直分支。
val messageJson = if (useStackedRows) {
    // rows 汇集 JSON 的 messageN 和 argsN 属性。
    val rows = new ArrayList<String>()
    // 为 bt 的主标签保留 message0。
    rows.add('''"message0": «toJsonString(bt.label ?: bt.typeName)»,
        "args0": [],''')
    // rowIndex 标识即将转换的输入。
    var rowIndex = 0
    // 并行遍历已准备好的标签和参数。
    while (rowIndex < rowArgs.size) {
        // Blockly 将第一行字段编号为 message1。
        val messageIndex = rowIndex + 1
        // 添加可见标签以及该行唯一的控件。
        rows.add('''"message«messageIndex»":
            «toJsonString(rowMessages.get(rowIndex))»,
            "args«messageIndex»": [«rowArgs.get(rowIndex)»],''')
        // 前进到 bt 的下一个输入。
        rowIndex++
    }
    // 合并这些属性，以插入块定义。
    rows.join("\n")
}
\end{lstlisting}

如果存在显式的 \texttt{message0}，如 \texttt{VisualFields} 中的情况，
生成器会尊重它，并保留作者声明的组合方式。在此例中，消息按照与属性
相同的顺序列出 \texttt{colour}、\texttt{angle}、\texttt{image} 和
\texttt{label}，而不会引入另一套显示名称。因此，同一实现既能生成
多行且易读的表单，也能在领域明确控制其消息时生成紧凑的可视块。

\begin{lstlisting}[float=htbp, style=tfmxtend, captionpos=t, caption={在 Blockly 工具箱中生成阴影块的带注释代码}, label={lst:toolbox-shadow-input}]
// 在 bt 中选择声明了阴影块类型的输入。
val shadowInputs = bt.valueInputs
    // it 是 Xtend 过滤器正在检查的 ValueInputSpec。
    .filter[it.shadowBlockType !== null].toList
// 当 bt 不需要阴影块时，保留普通条目。
if (shadowInputs.isEmpty) {
    // 生成没有附加配置的工具箱块。
    return '''{"kind": "block", "type": "«bt.typeName»"}'''
// 结束无阴影块的分支。
}
// 将每个 ValueInputSpec 转换为 Blockly 的 inputs 属性。
val inputsJson = shadowInputs.map['''
    // 使用输入名称作为所生成对象的键。
    "«it.name»": {
        // 声明 Blockly 应实例化为阴影块的类型。
        "shadow": { "type": "«it.shadowBlockType»" }
    // 结束当前输入的配置。
    }'''].join(",")
// 生成 bt 的工具箱条目及其所有阴影块。
'''{"kind": "block", "type": "«bt.typeName»", "inputs": {«inputsJson»
    }}'''
\end{lstlisting}

\begin{lstlisting}[float=htbp, style=tfmjava, captionpos=t, caption={Ecore 非包含引用转换的带注释代码}, label={lst:ecore-reference-conversion}]
// 在 rfs 中创建 eRef 引用的通用表示。
ReferenceFieldSpec rfs = new ReferenceFieldSpec();
// 保留 outgoing、source 或 target 作为控件名称。
rfs.setName(eRef.getName());
// 将选项限制为 Ecore 中声明的目标类型。
rfs.setTargetTypeName(eRef.getEReferenceType().getName());
// 复制原始引用的最小基数。
rfs.setLowerBound(eRef.getLowerBound());
// 规范化 -1 并复制最大基数。
rfs.setUpperBound(normalizeUpperBound(eRef.getUpperBound()));
// 保留 Ecore 是否要求值互不相同。
rfs.setUnique(eRef.isUnique());
// 保留值的顺序是否具有意义。
rfs.setOrdered(eRef.isOrdered());
// 检查 eRef 是否属于一对相反引用。
if (eRef.getEOpposite() != null) {
    // 保存将在浏览器中保持同步的相反端名称。
    rfs.setOppositeName(eRef.getEOpposite().getName());
// 结束相反端检查。
}
// 将下界一转换为显式必填性。
if (eRef.getLowerBound() >= 1) {
    // 启用必填引用验证。
    rfs.setRequired(true);
// 结束必填性推断。
}
// 复制控件、可见标签、顺序以及用作标签的字段。
applyUiAnnotation(eRef.getEAnnotation(UI_ANNOTATION_SOURCE), rfs);
// 如果注解未指定标签，则应用推断标签。
if (rfs.getReferenceLabelField() == null) {
    // 优先使用目标类型的标识符或描述性属性。
    rfs.setReferenceLabelField(
        defaultReferenceLabelField(eRef.getEReferenceType()));
// 结束引用标签的选择。
}
// 将 rfs 加入所属块类型 bt。
bt.getReferenceFields().add(rfs);
// 保留 eRef 在其他控件之间的原始位置。
bt.getOrderedInputNames().add(rfs.getName());
\end{lstlisting}

文本路线在 \texttt{DomainModelAdapter.convertReference} 中执行相同映射：
它从 \texttt{reference} 构造中获取类型、基数以及
\texttt{required}、\texttt{nonUnique}、\texttt{unordered} 和
\texttt{opposite} 选项。随后，生成器为单值引用选择下拉框，为多值
引用选择 \texttt{field\_reference\_multiselect}。运行时，
\texttt{updateReferenceDropdowns} 会重建候选项，
\texttt{synchronizeOppositeReferences} 则保持
\texttt{outgoing/source} 引用对同步。触发这两个操作的通用监听器将在
后文代码清单 \ref{lst:listener-runtime-blockly} 中详述。

该输入对的自动化测试会比较三个 \texttt{ReferenceFieldSpec}、各自的
标签、上下界、唯一性与顺序标志，以及相反端名称。随后，测试打开两个
编辑器，加载同一模型，并验证根对象为 \texttt{Workflow}、不存在警告，
且 XMI 导出保留标识和引用。

\texttt{actions} 输入。粗体属性表示必填值，\texttt{pageId} 还充当
模型标识符。\texttt{Navigate.target [1..1]} 引用指向现有的
\texttt{Page}，而不是表示新的包含关系。必填性、基数和唯一性规则由
这一结构推断得出；其他语义表达式则来自同一 Ecore 文件中的注解。

文本路线首先转换四种声明式变体。如果变体为 OCL，则先翻译受支持的
子集；其他变体直接提供其通用表达式。随后，代码清单
\ref{lst:add-validation-expression} 中的辅助方法创建中间规则。
\texttt{cls} 是规则求值所针对的领域类；\texttt{spec} 是正在构建的
中间编辑器；\texttt{name}、\texttt{expression} 和 \texttt{message}
来自声明；\texttt{vs} 是新规则；\texttt{visualExpression} 则是它可选
的、更基础块形式的展开。

\begin{lstlisting}[float=htbp, style=tfmjava, captionpos=t, caption={在 Java 中转换文本验证规则的带注释代码}, label={lst:add-validation-expression}]
// 接收类 cls、编辑器 spec 以及规则的三个文本值。
private static void addValidationExpression(
    // cls 是目标，spec 是待扩展的中间模型。
    ClassDef cls, BlocklyEditorSpec spec,
    // name 标识规则；expression 和 message 定义其行为。
    String name, String expression, String message) {
    // 丢弃没有可执行条件的声明。
    if (expression == null || expression.isBlank()) return;
    // 创建 vs，作为规则的通用表示。
    ValidationSpec vs = new ValidationSpec();
    // 所有声明式变体均汇合为 EXPRESSION 类型。
    vs.setType(ValidationSpec.ValidationType.EXPRESSION);
    // 组合类名和规则名，避免规则之间发生名称冲突。
    vs.setName(cls.getName() + "_" +
        (name == null || name.isBlank() ? "validation" : name));
    // 记录对 vs 求值的块类。
    vs.setOwnerType(cls.getName());
    // 移除首尾空白，并将文本保存在 trimmed 中。
    String trimmed = expression.trim();
    // 保存将在浏览器中执行的表达式。
    vs.setExpression(trimmed);
    // 尝试将 trimmed 转换为可视访问器树。
    ValidationExpressionSpec visualExpression = ValidationExpressionParser
        // 根据 cls 的元素类型调整 size(...)。
        .parse(trimmed, fieldName -> sizeAccessorExpression(cls, fieldName))
        // null 表示只保留文本表达式。
        .orElse(null);
    // 如果解析器可以构建可视展开，则保存该展开。
    vs.setVisualExpression(visualExpression);
    // 始终创建图中显示的外层块。
    vs.setVisualBlock(ValidationBlockSpec.expressionRule(
        cls.getName(), trimmed, visualExpression));
    // 使用声明的消息；若没有，则构建默认的描述性消息。
    vs.setMessage(firstNonBlank(message,
        "Constraint \"" +
        (name == null || name.isBlank() ? "validation" : name) +
        "\" is violated on " + cls.getName() + "."));
    // 将完成的规则加入编辑器的通用列表。
    spec.getValidations().add(vs);
// 结束该声明的转换。
}
\end{lstlisting}

Ecore 路线在遍历验证注解的 \texttt{expression.*}、
\texttt{condition.*}、\texttt{js.*} 和 \texttt{ocl.*} 详情时执行等价
操作。随后，两条路线都会复用 \texttt{generateValidationsJs}。对于
输入 \texttt{home}，生成的代码读取 \texttt{route} 字段，将表达式
求值为假，并把消息交给 \texttt{queueWarn}；
\texttt{applyValidationWarnings} 会将其放到块上和问题选项卡中。代码
清单 \ref{lst:listener-runtime-blockly} 中的监听器会在每次更改后重复
计算。

该输入对的验证过程会比较十二条规则、各自的可视树和执行表达式。
随后，它使用有效模型打开两个编辑器，确认不存在警告，并检查
\texttt{validation\_blocks.json}、可视化环境和
\texttt{validation\_runtime.js} 是否保持同步。
