\chapter{Model2Blockly 的实现}
\label{chap:implementacion}

本章按照一次完整执行的流程说明 Model2Blockly 的实现。与上一章侧重
设计和架构不同，本章将指出生成链各阶段所对应的具体技术、类和操作。

本章首先说明如何在第一个限定示例上运行该工具，以及如何找到生成的
编辑器。随后介绍内部流程、代码组织，以及六组互补示例；每组示例均由
\texttt{source.ecore} 和 \texttt{source.m2b} 配对构成。在这些输入对之外，
还增加了一个专门展示 Ecore 独有能力的案例。这组案例将本章后文讨论的
各项规则分开呈现。在此基础上，本章详细介绍输入的加载与验证、
\texttt{EditorSpec} 契约、Java 适配器、HTML/JavaScript 生成器，以及
浏览器中的运行行为。最后介绍 Eclipse 集成与分发、独立入口和实现测试。

\section{运行 Model2Blockly}
\label{sec:ejecucion-model2blockly}

在详细介绍内部类之前，本节先从用户角度说明可以直接观察到的操作过程。
运行 Model2Blockly 的主要方式是使用其 Eclipse 插件。该环境必须使用
Java 21 启动；插件既可以从项目发布的 p2 仓库安装，也可以从源代码启动
一个 Eclipse 运行时实例来执行。无论采用哪种方式，生成操作都作用于
工作区中的输入文件。

这里使用 \path{examples/feature_pairs/01_basic_structure} 输入对来复现
执行过程，因为它只包含观察完整生成链所需的元素：一个包、一个抽象类、
若干具体类、一条继承关系、一条包含关系和若干工具箱分类。图
\ref{fig:basic-structure-ecore} 展示了该示例 Ecore 元模型的结构视图。
这里采用类图而不是 XML 序列化形式，使读者无需接触 Ecore 的持久化细节，
即可识别其中的类、类型和关系。

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.96\textwidth]{../../io.github.plortinus.model2blockly/examples/feature_pairs/01_basic_structure/basicStructure class diagram.jpg}
  \caption{输入对 \texttt{01\_basic\_structure} 的 Ecore 类图}
  \label{fig:basic-structure-ecore}
\end{figure}

\texttt{Board} 是该示例的根类。其 \texttt{name} 属性类型为
\texttt{EString}，默认值为 \texttt{Sprint board}。\texttt{items} 关系
上的实心菱形表示包含关系，基数 \texttt{[1..4]} 则要求每个看板包含
一至四个元素。在生成的编辑器中，该引用会转换为一个语句输入，其中可以
接入兼容的块。

\texttt{WorkItem} 是抽象类，因此不会生成为可实例化的块。其子类
\texttt{Task} 和 \texttt{Note} 会生成块，并可插入 \texttt{items}。
\texttt{Task} 的属性覆盖了三种转换：\texttt{title} 表示为文本字段，
\texttt{priority} 表示为根据枚举 \texttt{Priority} 构造的下拉列表，
而 \texttt{done} 表示为布尔字段。\texttt{Note} 的 \texttt{body}
属性则生成另一个文本字段。

最后，\texttt{Tag} 用于检验一个独立的具体类同样会转换为块类型。该图
有意省略了用于指定展示选项的 \texttt{blockly} 注解，例如
\texttt{inputsInline=false}；这些注解仍保留在 \texttt{source.ecore}
中，但理解图中所表示的领域结构并不需要它们。基于这一输入，Ecore 路线
按以下步骤执行：

\begin{enumerate}
  \item 在 Eclipse 中打开或导入主项目；
  \item 在该目录中选择 \path{source.ecore} 文件；
  \item 从上下文菜单执行 \texttt{Model2Blockly -> Generate Blockly Editor}；
  \item 查看生成结束后 Eclipse 自动打开的报告
  \path{source_generated/generation_report.html}；
  \item 在浏览器中打开位于 \path{source_generated/html/} 的
  \path{BasicStructure_standalone.html}，使用生成的编辑器。
\end{enumerate}

文本路线的运行方式相同，只需选择同一目录中的 \path{source.m2b}。
在这两种情况下，如果没有检测到错误，工具都会在输入文件旁创建一个以后缀
\texttt{\_generated} 命名的目录。该目录包含生成报告、\texttt{EditorSpec}
的 XMI 序列化、块定义、工具箱、生成与验证脚本、示例模型以及编辑器的
HTML 页面。由于两个文件都名为 \texttt{source}，交互式运行时需要分别
执行。为同时保留两种输出，仓库还提供了 \texttt{npm run
generate:feature-pairs}；该命令会分别将它们写入 \path{generated/ecore}
和 \path{generated/dsl}。

需要区分这里涉及的两次执行。第一次在 Eclipse 中进行，把领域描述转换为
Web 产物。第二次发生在浏览器中，即打开独立页面
\texttt{*\_standalone.html} 之后；用户可在其中使用块构建领域模型、执行
生成的验证，并将结果导出为 JSON、XMI 或文本代码。图
\ref{fig:basic-structure-editor} 展示了 \texttt{01\_basic\_structure}
的第二次执行，其中示例模型已经加载到工作区。由 \texttt{source.m2b}
生成的编辑器具有相同外观，因为两条路线会产生同一个中间描述符和相同的
Web 产物。

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\textwidth]{../../io.github.plortinus.model2blockly/examples/feature_pairs/01_basic_structure/screenshots/ecore.png}
  \caption{由 \texttt{source.ecore} 生成的
  \texttt{01\_basic\_structure} Blockly 编辑器（已加载示例模型）}
  \label{fig:basic-structure-editor}
\end{figure}

以下各节将逐步展开这条生成链，并把每个可见操作与其实现对应起来。

在 Ecore 分支中，EMF 加载资源并取得一个 \texttt{EPackage}；在文本分支
中，Xtext 先解析、链接并验证文件，再取得一个 \texttt{DomainModel}。
Java 适配器把这两个对象都转换为 \texttt{EditorSpec} 实例。此后执行过程
完全共用：先检查模型，将其序列化为 XMI，再重新加载并再次验证，最后交给
Xtend 生成器。

生成器返回一张从路径到文本内容的映射表。处理器创建输出目录、写入映射
中的每一项，并刷新 Eclipse 工作区。最后这一步解释了为什么一次操作会生成
多个彼此相关的文件，而不只是上一节展示的独立页面。后续各节将详细介绍图中
每个方框所概括的操作。

\section{项目组织}
\label{sec:organizacion-proyecto}

本实现按照 Xtext 的常见结构，分布在三个可执行 OSGi bundle 中
\cite{xtextProject}。项目 \path{io.github.plortinus.model2blockly} 包含
语法、通用 EMF 模型、适配器、验证、生成器和命令行入口。以 \path{.ide}
结尾的项目提供独立于界面的语言服务配置。最后，以 \path{.ui} 结尾的项目
注册编辑器、菜单和处理器，从而把生成过程连接到 Eclipse 工作区。

另外两个项目不会为转换增加逻辑。\path{.feature} 项目聚合可安装的 bundle，
\path{.updatesite} 则构建用于分发插件的 p2 仓库。在这三个可执行 bundle
中，表 \ref{tab:paquetes-implementacion} 将每个组件与实现它的文件和所用
技术对应起来。

尤其需要说明，表中的“适配器”对应两个手工编写的 Java 类，而不是 Xtext
生成的转换代码。它们的公开方法接收已经加载的 EMF 对象：第一条路线接收
一个 \texttt{EPackage}，第二条路线接收一个 \texttt{DomainModel}。
两个类都通过各自的类型化 API 遍历这些对象，并把最终的 EMF
\texttt{EditorSpec} 实例的创建委托给 \texttt{BlocklySpecModelMapper}。
第 \ref{sec:implementacion-ecore-adapter} 节和第
\ref{sec:implementacion-domainmodel-adapter} 节将详细说明每个类所采用的规则。

这种组织方式落实了上一章的架构，而没有重复其内容：上一章论证组件及其
依赖关系，本章则指出执行这些职责的具体类、语言和产物。

这六组示例合起来覆盖了 Ecore 和 DSL 都能够表达的能力。把它们分开，可以
让每个示例主要负责一类能力，并避免使用一个难以阅读的庞大元模型。可复现的
矩阵 \path{examples/feature_pairs/CAPABILITY_MATRIX.md} 列举每项能力，
为其指定一个主要示例，并定义必须在 \texttt{EditorSpec}、生成产物或实际
运行的编辑器中出现的证据。

案例 \path{examples/ecore_specific/07_ecore_specific} 则补充覆盖了
子包、被忽略的特征、接口类、更多数值类型、引用标签的自动选择、显式命名
空间 URI 与前缀，以及 Ecore/OCL 标准注解容器。它不被视为第七个输入对，
因为 DSL 没有对应构造；若比较两条路线，只会形成一种人为的等价关系。

这种组织方式使每幅图和每段代码清单都能聚焦于一项具体决策，并让读者把
源文件、转换和最终编辑器联系起来。特别是，\texttt{03\_composition\_inputs}
用于说明组合，而 \texttt{04\_references\_integrity} 则单独说明非包含引用。

这些输入对同时也是可执行的回归测试案例。可以从仓库根目录运行以下命令
启动完整验证：

\begin{center}
  \texttt{npm run verify:feature-pairs}
\end{center}

该脚本加载六个输入对各自的两个源文件。随后分别执行
\texttt{EcoreAdapter} 和
\texttt{DomainModel}\allowbreak\texttt{Adapter}，序列化并重新加载两个
中间模型，再比较 \texttt{EditorSpec} 的规范化表示。接着，它要求两条
路线生成同一组主要产物，并通过浏览器冒烟测试打开生成的十二个编辑器
---六个输入对乘以两条路线---。最后，它还生成 Ecore 独有案例，检查其七组
能力并打开对应编辑器。因此总共验证十三个编辑器。借助这一检查，这些示例
既可用于解释实现，也可以证明当两种表示法表达相同能力时，它们会到达同一个
通用契约。

\section{输入的加载与验证}
\label{sec:carga-validacion-entradas}

加载发生在适配之前。\texttt{EcoreAdapter} 接收一个已经构造好的 EMF
对象，\texttt{DomainModelAdapter} 则接收 Xtext 生成的类型化模型；这两个
类都不负责打开文件。在 Eclipse 中执行时，这项职责属于
\texttt{GenerateBlocklyEditorHandler}；独立入口类对工作区外的文件复现
同样的模式。该阶段的结果是一个可作为转换起点的有效
\texttt{EPackage} 或 \texttt{DomainModel}。

\subsection{加载 \texttt{.ecore} 元模型}

\texttt{generateFromEcore} 方法为 \texttt{ecore} 扩展名注册
\texttt{EcoreResource}\allowbreak\texttt{FactoryImpl}，创建一个
\texttt{ResourceSet}\allowbreak\texttt{Impl}，
并根据所选资源的位置构造文件 URI。调用 \texttt{getResource(uri, true)}
会请求立即加载 XMI 文档，随后 EMF 解析其中的元素和引用。第一个根对象
作为 \texttt{EPackage} 取得，并传给 \texttt{EcoreAdapter}。
\texttt{EcoreToBlocklyMain} 类在其 \texttt{loadEPackage} 方法中使用
相同的流程。

这条分支不使用 Xtext 的解析器或验证器。导致资源无法读取的问题会作为加载
异常继续传播；生成器所需的特定约束则在适配之后由
\texttt{BlocklySpecDiagnostics} 检查。这种分离避免把已经采用 EMF 标准
格式的元模型误作文本语法来解释。

\subsection{加载并验证 \texttt{.m2b} 输入}

文本路线首先使用 \texttt{Model2BlocklyStandalone}\allowbreak\texttt{Setup}
注册语言。Xtext 生成的配置把同一种语言同时关联到 \texttt{.m2b} 和
\texttt{.model2blockly} 扩展名；后者为保持兼容性而保留。Guice 注入器
提供 \texttt{ResourceSet}，后者把文件加载为 \texttt{XtextResource}。
解析器创建 EMF 树，链接器解析分类、父类和类型所使用的名称。如果加载成功，
资源的第一个元素必须是 \texttt{DomainModel} 实例。

代码清单 \ref{lst:carga-modelo-m2b} 汇总了处理器中实现该阶段的 Java
调用。独立入口类 \texttt{Model2BlocklyTo}\allowbreak\texttt{BlocklyMain}
包含同样的调用
序列，唯一的区别是文件路径的来源。

\begin{lstlisting}[style=tfmjava, captionpos=t, caption={加载并验证 \texttt{.m2b} 输入的带注释流程}, label={lst:carga-modelo-m2b}]
// 创建 DSL 的独立配置。
Injector injector = new Model2BlocklyStandaloneSetup()
    // 向 EMF 注册 Xtext 生成的元素。
    .createInjectorAndDoEMFRegistration();
// 获取由 Guice 配置的资源集。
ResourceSet resourceSet = injector.getInstance(ResourceSet.class);
// 加载 URI，并执行解析和链接。
Resource resource = resourceSet.getResource(fileUri, true);
// 保留 Xtext 类型，以访问其服务。
XtextResource xtext = (XtextResource) resource;

// 检查模型是否符合具体语法。
xtext.validateConcreteSyntax();
// 传播语法错误和链接错误。
Model2BlocklyValidationDiagnostics.throwIfSyntaxErrors(
    // 标识来源，并传入资源错误。
    sourceLabel, resource.getErrors());
// 传播 DSL 语义规则产生的错误。
Model2BlocklyValidationDiagnostics.throwIfErrors(
    // 将诊断与输入文件关联。
    sourceLabel,
    // 获取为该语言注册的验证器。
    xtext.getResourceServiceProvider().getResourceValidator()
        // 对资源执行全部 @Check 规则。
        .validate(resource, CheckMode.ALL,
            // 表明此次验证不会被取消。
            CancelIndicator.NullImpl));

// 声明文本模型的类型化根对象。
DomainModel domain =
    // 获取 Xtext 生成的第一个 EMF 对象。
    (DomainModel) resource.getAllContents().next();
\end{lstlisting}

上述调用覆盖两类问题。第一次检查收集解析和链接期间产生的错误；第二次执行
\texttt{Model2BlocklyValidator} 的 \texttt{@Check} 规则。这些规则能够
检测多种情况，包括类名重复、基数不一致、值输入类型无效、控件不兼容、引用
不存在的字段，以及不受支持的验证表达式。\texttt{throwIfErrors} 方法只在
诊断严重级别为 \emph{error} 时停止生成；警告仍会显示在编辑器中，但允许
生成继续进行。

\subsection{验证层级与错误传达}

该实现依次应用三个验证层级。首先检查资源是否能够加载；在文本路线中，还会
检查语法和引用是否正确。随后执行 DSL 特有的语义规则。最后，在调用对应的
适配器后，\texttt{BlocklySpecDiagnostics.assertValid} 检查通用
\texttt{EditorSpec} 的不变量。对 XMI 完成序列化和重新加载后，会再次执行
最后这项验证，因此生成器只会接收已通过完整中间契约检查的模型。

在 Eclipse 中执行时，语义错误和通用模型诊断会转换为与文件关联的
\texttt{IMarker.PROBLEM} 标记；如果存在来源信息，标记还会关联到具体行。
处理器会重新打开输入文件，并用对话框显示摘要。在独立入口中，同一诊断会
写入错误输出，进程以非零状态码结束。因此，两种执行方式共用相同的检查，
只是通过不同界面呈现结果。

\section{使用 Xtext 的文本路线 \texttt{.m2b}}
\label{sec:implementacion-xtext}

Xtext 语法定义文本输入语言 \texttt{.m2b}，并把其规则与相关 EMF 元模型
中的概念绑定。Xtext 根据该语法生成解析器和编辑支持
\cite{xtextProject,bettini2013xtext,bettini2015xsemantics}。因此，每个
DSL 文件都可以作为 EMF 模型处理。该模型的根对象汇集领域名称、生成选项、
工作区配置、分类、类和约束。

领域类使用 DSL 的专门构造声明。每个类都可以是抽象类、生成输出块、继承
另一个类、归属某一分类，并定义颜色、标签、工具提示、行内布局和代码模板。
类中可以声明四类元素：属性、包含关系、引用和值输入。语法中的这一区分对应
Blockly 表示信息的几种主要形式：字段、语句输入、引用下拉框和值连接器。

DSL 还包括界面选项。利用这些选项，可以指定控件、标签、帮助文本、分组、
展示顺序、只读字段、隐藏字段，以及用于显示引用的字段。基本 Blockly 编辑器
并不需要这些信息，但它们可以在无须手写 JavaScript 的情况下丰富生成的
输出。本论文通过小型示例使用这些信息说明它与 Ecore 的对应关系，同时避免
把文本表示法和 Xtext 所生成的元模型混为一谈。

代码清单 \ref{lst:composition-inputs-dsl} 和
\ref{lst:references-integrity-dsl} 分别展示了前文同时涉及的两项决策。
前者说明如何声明组合和值输入，后者只涉及标识和非包含引用。每条包含在清单
中的语句都由 \texttt{//} 注释说明。Ecore 适配器一节中的图
\ref{fig:ecore-composition-acotado} 和
\ref{fig:ecore-references-acotado} 展示了相应结构，而没有复现 XML。

\begin{lstlisting}[style=tfmm2b, captionpos=t, caption={逐行注释的 \texttt{03\_composition\_inputs} 关键片段}, label={lst:composition-inputs-dsl}]
// 命名将被转换为 EditorSpec 的领域。

// 为结构块创建分类。
category Composition colour 200
// 为输出块创建另一个分类。
category Expressions colour 230

// 将 Document 声明为组合结构的根块。
class Document category Composition colour 200 inputsInline false {
  // 创建语句输入 sections，可容纳一至四个 Section。
  contains Section sections [1..4]
    // 将 sections 显示为标题为 Sections、顺序为第二的插槽。
    widget slot uiLabel "Sections" order 2 variant default
// 结束 Document 块的声明。
}

// 声明通用类型 Section，但不创建可实例化的块。
abstract class Section category Composition colour 120 inputsInline false {
// 结束抽象父类型 Section 的声明。
}

// 将 Paragraph 声明为与 Section 兼容的具体块。
class Paragraph extends Section category Composition colour 120 inputsInline false {
  // 创建值输入 content，其类型为 TextExpression。
  value TextExpression content shadow TextLiteral
    // 将 content 显示为标签为 Content 的表达式插槽。

// 结束 Paragraph 的声明。
}

// 声明用于定义可接受输出连接的抽象类型。
abstract output class TextExpression category Expressions colour 230 inputsInline false {
// 结束抽象类型 TextExpression 的声明。
}

// 创建具体影子块，并将其输出指定为 TextExpression。
output as TextExpression class TextLiteral extends TextExpression
  // 将该具体块放入 Expressions 分类。

// 结束 TextLiteral 的声明；此处省略其文本属性。
}
\end{lstlisting}

在该片段中，\texttt{sections} 和 \texttt{content} 是 Blockly 输入的
内部名称，而不是 Java 变量。\texttt{contains} 构造生成一个可堆叠块的
语句输入；\texttt{value} 则生成水平输入。\texttt{TextExpression}
是可接受的连接类型，\texttt{TextLiteral} 是默认显示的影子块，直到用户
接入另一个兼容表达式。

\begin{lstlisting}[style=tfmm2b, captionpos=t, caption={逐行注释的 \texttt{04\_references\_integrity} 关键片段}, label={lst:references-integrity-dsl}]
// 命名专门用于标识和引用的领域。
domain ReferencesIntegrity
// 为示例中的块创建通用分类。
category References colour 260

// 将 Card 声明为流程中的具体元素。
class Card extends Element category References colour 120 inputsInline false {
  // 使用 cardId 作为每张卡片的稳定标识。
  attribute cardId : string [1..1] default "card-1" modelId
  // 允许选择最多三个 Link，并将 source 声明为相反端。
  reference Link outgoing [0..3] opposite source unique ordered
    // 为 outgoing 生成一个根据工作区更新的选择器。
    widget reference-select uiLabel "Outgoing links" order 3 variant default

    referenceLabelField linkId
// 结束 Card 的声明。
}

// 将 Link 声明为流程中的第二个具体元素。
class Link extends Element category References colour 120 inputsInline false {
  // 使用 linkId 作为每条链接的稳定标识。
  attribute linkId : string [1..1] default "link-1" modelId
  // 要求一个来源 Card，并与 Card.outgoing 保持同步。
  reference Card source [1..1] opposite outgoing required unique ordered
    // 使用已有卡片选择器表示 source。
    widget reference-select uiLabel "Source card" order 2 variant default
    // 在选择器选项中显示 Card 的 title 字段。
    referenceLabelField title

  reference Card target [1..2] required nonUnique unordered
    // 使用另一个引用选择器表示 target。
    widget reference-select uiLabel "Target cards" order 4 variant default

// 结束 Link 的声明。
}
\end{lstlisting}

这里，\texttt{cardId} 和 \texttt{linkId} 是被标记为标识符的领域属性；
即使可见标签发生变化，编辑器也能借助它们保留引用。\texttt{outgoing}、
\texttt{source} 和 \texttt{target} 是模型中的引用名称。
\texttt{opposite} 连接必须保持同步的两个端点，\texttt{referenceLabelField}
则决定下拉框中显示哪个便于用户理解的属性，而不会替换持久化的标识符。

按照第 \ref{sec:carga-validacion-entradas} 节所述流程解析文件后，该语法
会得到一个已完成链接和验证的 \texttt{DomainModel}。这个对象就是第
\ref{sec:implementacion-domainmodel-adapter} 节后续介绍的 Java 适配器的输入。

\section{EMF 中间模型与 Java 视图}
\label{sec:implementacion-modelo-intermedio}

中间模型的契约以 EMF 元模型的形式定义在 \texttt{model} 目录下的
\path{blockly_editor_spec.ecore} 文件中。EMF 根据该文件生成
\texttt{EditorSpec}、\texttt{BlockTypeSpec}、\texttt{FieldSpec} 等
\path{intermediate.blocklyspec} 包中的 Java 接口，以及
\texttt{BlocklySpecFactory}。为便于构造这些实例，项目还保留了
\texttt{BlocklyEditorSpec}，作为同一内容的辅助 Java 视图。
\texttt{BlocklySpecModel}\allowbreak\texttt{Mapper} 实现该视图与 EMF
工厂所创建实例之间的
双向复制。

适配完成后，EMF 对象不会直接传给生成器。序列化过程封装在
\texttt{BlocklySpecXmi}\allowbreak\texttt{Serializer} 中。该类创建
\texttt{ResourceSet}\allowbreak\texttt{Impl}，注册
\texttt{BlocklySpecPackage.}\allowbreak\texttt{eNS\_URI}，并把
\texttt{EditorSpec} 添加到 URI 为
\texttt{memory:/}\allowbreak\texttt{blocklyspec.xmi} 的
\texttt{XMIResource}\allowbreak\texttt{Impl} 中。资源以 UTF-8 保存，
再从该字符串重新加载，并检查其根对象是否仍为 \texttt{EditorSpec}。
代码清单 \ref{lst:ciclo-editor-spec-xmi} 展示处理器如何在两条输入路线中
应用这一循环。

\begin{lstlisting}[float=htbp, style=tfmjava, captionpos=t, caption={中间模型的验证、序列化与重新加载（含注释）}, label={lst:ciclo-editor-spec-xmi}]
// 验证适配器创建的通用模型。
BlocklySpecDiagnostics.assertValid(intermediateModel, sourceLabel,
    // 用于把每项错误关联到源模型。
    sourceMapper);

// 声明用于保存中间 XMI 的字符串。
String intermediateXmi =
    // 将 EditorSpec 序列化为内存中的 XMI 资源。
    BlocklySpecXmiSerializer.toXmi(intermediateModel);
// 声明将用于生成编辑器的模型。
EditorSpec spec =
    // 重新加载 XMI，并检查其根对象是否为 EditorSpec。
    BlocklySpecXmiSerializer.fromXmiToEditorSpec(intermediateXmi);

// 重新加载后再次验证模型。
BlocklySpecDiagnostics.assertValid(
    // 将本次检查标识为中间 XMI 的检查。
    spec, sourceLabel + " intermediate XMI");
// 声明生成文件的有序映射。
Map<String, String> generated =
    // 将通过验证的 EditorSpec 转换为 HTML 和 JavaScript。
    new BlocklyCodeGenerator().generate(spec);
\end{lstlisting}
\FloatBarrier

在该片段中，\texttt{sourceMapper} 表示根据所用路线由
\texttt{forEPackage} 或 \texttt{forDomainModel} 创建的映射器。第一次
诊断可通过 \texttt{sourceMapper} 关联到源模型中的元素；第二次诊断则验证
重新加载的对象。这样，序列化错误、根对象错误或必填数据丢失都会在生成文本
之前被发现。同一 XMI 字符串随后保存在
\path{intermediate/*_blocklyspec.xmi} 中，因此可供检查的产物正是用于
生成编辑器的实际内容。

每种块类型都保存自己的连接形式：根块、可堆叠块、类型化可堆叠块、值块或
类型化值块。借助这种分类，可以在不把 Blockly 特有规则与领域读取过程混在
一起的情况下生成适当的可视化连接。此外，实现还分别维护字段、语句输入、
引用和值输入列表，从而便于使用对应的 Blockly 构造生成每类元素。

中间模型还保留块中各输入的顺序信息。这一决策对 Ecore 路线尤其重要：从
元模型读取类的特征时，属性和引用的原始顺序可能影响生成块的可读性。若该
列表存在，生成器就使用它；否则采用默认顺序。

这一实现的优势是解耦。各输入适配器都会生成符合同一个中间元模型的实例，
生成器则使用其 Java 视图，而不依赖实例的创建方式。因此，代码中的输入与
输出相互分离，同时 MDE 契约仍由 EMF 元模型及其 XMI 序列化定义。

\section{Ecore 适配器}
\label{sec:implementacion-ecore-adapter}

\subsection{入口点与通用规范化}

两个适配器都实现为带有静态方法的普通 Java 类；它们既不需要实例化，也不
包含生成模板。代码清单 \ref{lst:entrada-adaptadores-java} 展示它们的实际
入口点。每个方法先将输入规范化为 \texttt{BlocklyEditorSpec}。这是一个由列表
和类型化对象组成的内部 Java 视图；随后再调用
\texttt{BlocklySpecModelMapper.toEmfSpec}。第二步使用
\texttt{BlocklySpecFactory.eINSTANCE} 创建通用元模型定义的
\texttt{EditorSpec}，并递归复制分类、块、字段、输入、验证和工作区选项。
因此，Java 视图只是用于构造的辅助对象；适配器的契约结果是 EMF
\texttt{EditorSpec} 实例。

\begin{lstlisting}[float=htbp, style=tfmjavaecore, caption={两个适配器的 Java 入口点}, label={lst:entrada-adaptadores-java}]
// 声明 EcoreAdapter.java 的入口点。
public static EditorSpec toEditorSpec(EPackage pkg) {
    // 遍历 EPackage，并把 Java 视图转换为通用 EMF 模型。
    return BlocklySpecModelMapper.toEmfSpec(fromEPackage(pkg));
// 结束 Ecore 适配路线。
}

// 声明 DomainModelAdapter.java 的入口点。
public static EditorSpec toEditorSpec(DomainModel domain) {
    // 遍历 DomainModel，并创建同一个通用 EMF 模型。
    return BlocklySpecModelMapper.toEmfSpec(fromDomainModel(domain));
// 结束文本适配路线。
}
\end{lstlisting}

在第一个方法中，\texttt{pkg} 是从 \texttt{source.ecore} 加载的 Ecore
包。在第二个方法中，\texttt{domain} 是 Xtext 解析
\texttt{source.m2b} 时构造的文本模型树。二者都是输入对象；两个方法均
返回 \texttt{EditorSpec}，也就是同一种 EMF 中间模型，尽管其来源不同。

\subsection{包的遍历与类的转换}

在 Ecore 路线中，\texttt{fromEPackage} 接收在第
\ref{sec:carga-validacion-entradas} 节所述加载过程中取得的对象。该方法
首先复制包的名称、\texttt{nsURI}、前缀和全局选项。然后，它收集作为某条
包含引用目标的类名；后续会用这个集合区分根块与应作为子元素连接的块。接着，
该方法遍历包及其子包中的全部 \texttt{EClassifier}，选出
\texttt{EClass}，并调用 \texttt{convertEClass}。该过程直接使用 EMF
API 中的类、属性、引用、继承和基数概念 \cite{emfOverview}。

代码清单 \ref{lst:recorrido-eclass-ecore} 只保留了执行类分派的循环。
全局选项的读取以及后续验证生成在此省略，因为它们不参与这里展示的决策。
该片段来自 \texttt{fromEPackage} 方法，并非伪代码。

该片段中的数据方向为
\texttt{eClass} $\rightarrow$ \texttt{bt} $\rightarrow$ \texttt{spec}：
一个 Ecore 类生成一个块描述符，随后该描述符加入编辑器描述符。
\texttt{categoryMap} 参数是把每个分类名称映射到其
\texttt{CategorySpec} 的映射；\texttt{containedTypeNames} 是所有作为
包含关系目标出现的类名集合。后者用于随后判断一个类代表根元素还是子元素。

\begin{lstlisting}[float=htbp, style=tfmjavaecore, captionpos=t, caption={遍历 Ecore 类的带注释代码片段}, label={lst:recorrido-eclass-ecore}]
// 遍历包及其子包中的分类器。
for (EClassifier classifier : allClassifiers(pkg)) {
    // 只保留表示 Ecore 类的分类器。
    if (classifier instanceof EClass) {
        // 使用 EMF API 提供的类型取得该类。
        EClass eClass = (EClass) classifier;
        // 创建 bt，即由 eClass 得到的块描述符。
        BlockTypeSpec bt = convertEClass(
            // 传入类、分类以及被包含类型。
            eClass, categoryMap, containedTypeNames);
        // 将 bt 加入正在构造的编辑器 spec。
        spec.getBlockTypes().add(bt);
    // 结束当前 EClass 的处理。
    }
// 结束分类器遍历。
}
\end{lstlisting}
\FloatBarrier

把该循环应用于图 \ref{fig:basic-structure-ecore} 时，会分别为
\texttt{Board}、\texttt{WorkItem}、\texttt{Task}、\texttt{Note} 和
\texttt{Tag} 调用 \texttt{convertEClass}。每次调用都会创建一个
\texttt{BlockTypeSpec}。\texttt{WorkItem} 的 \texttt{isAbstract}
属性会复制到该描述符，因此这个类型参与连接检查，却不会在工具箱中作为可实例化
的块提供。

从 MDE 的角度看，该适配器是一项基于 EMF API、以 Java 实现的模型转换。
本项目没有使用 ATL 或 ETL 之类的专用转换语言。原因是实际工程需求：生成器
需要集成到 Eclipse/Xtext 插件中，复用项目的 Java 工具类，对输入文件发出
具体诊断，并构造随后序列化为 XMI 的 EMF \texttt{EditorSpec} 实例。
因此，实现可以保留在加载资源并向 Eclipse 环境传达错误的同一条 Java
执行链中。表 \ref{tab:transformacion-ecore-editor-spec} 汇总了该转换的
主要规则。

\subsection{属性与枚举的转换}

在遍历类的过程中，每个可编辑属性都会被处理。
\texttt{convert}\allowbreak\texttt{EAttribute} 方法创建一个
\texttt{FieldSpec}，并根据 \texttt{EDataType} 选择其可视化表示。
代码清单 \ref{lst:conversion-eattribute} 展示
\texttt{01\_basic\_structure} 所用的分支；数值、颜色、角度和图像分支
遵循同一模式，且不参与本示例，因此在此省略。

在代码中，\texttt{eAttr} 是 \texttt{convertEAttribute} 接收的 Ecore
属性；\texttt{fs} 是输出 \texttt{FieldSpec}，已在方法开头创建；
\texttt{type} 保存 \texttt{eAttr} 的数据类型；\texttt{lit} 则表示每次
迭代处理的枚举字面量。转换方向是
\texttt{eAttr} $\rightarrow$ \texttt{fs}；随后 \texttt{fs} 会加入
\texttt{bt} 的字段列表。该片段从 \texttt{fs} 创建之后开始，因此没有
重复其初始化过程。

\newpage
\begin{lstlisting}[style=tfmjavaecore, captionpos=t, caption={Ecore 属性转换的带注释代码片段}, label={lst:conversion-eattribute}]
// eAttr 是输入属性；type 保存其 EDataType。
EDataType type = eAttr.getEAttributeType();
// 检查该属性是否使用领域枚举。
if (type instanceof EEnum) {
    // eEnum 是与 eAttr 关联的枚举类型。
    EEnum eEnum = (EEnum) type;
    // fs 是输出字段；将其配置为下拉框。
    fs.setFieldType(FieldSpec.FieldType.DROPDOWN);
    // lit 是本次迭代处理的字面量。
    for (EEnumLiteral lit : eEnum.getELiterals()) {
        // 使用 lit 的名称和值向 fs 添加一个选项。
        fs.getOptions().add(new DropdownOption(
            lit.getName(), lit.getLiteral()));
    }
// 处理不是枚举的其他数据类型。
} else {
    // 根据 type 的名称选择 fs 的表示形式。
    switch (type.getName()) {
        // 将字符串转换为文本字段。
        case "EString":
            // 将 fs 配置为文本字段。
            fs.setFieldType(FieldSpec.FieldType.TEXT); break;
        // 本片段省略数值类型分支。
        // 将逻辑值转换为布尔复选框。
        case "EBoolean":
            // 将 fs 配置为布尔字段。
            fs.setFieldType(FieldSpec.FieldType.BOOLEAN); break;
    }
}
\end{lstlisting}

在该示例中，这项决策产生了图 \ref{fig:basic-structure-editor} 中三个
可以观察到的结果：类型为 \texttt{EString} 的 \texttt{Task.title}
转换为文本字段；类型为枚举 \texttt{Priority} 的
\texttt{Task.priority} 生成包含 \texttt{low}、\texttt{medium} 和
\texttt{high} 的下拉框；类型为 \texttt{EBoolean} 的
\texttt{Task.done} 则表示为布尔字段。完成类型选择后，同一方法还会复制
默认值，并在 \texttt{lowerBound} 大于或等于一时把字段标记为必填。
